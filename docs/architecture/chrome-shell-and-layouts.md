# Chrome Shell & Layouts

This guide elaborates on WIS.md. If anything here conflicts, WIS.md wins.

## Frontend structure

The React/TypeScript chrome lives in `crates/shell/src/`. Imports use `@/...` aliases; relative cross-module imports are forbidden. The bundle is **window-agnostic**: it reads its own label from `getCurrentWindow()` and routes tab/overlay/peek/widget work to that window, so a secondary window behaves exactly like `main` over its own workspace.

- **Components** (`src/components/`): `Window` (root layout host), chrome frame (`TopBar`/`NavRow`/`TopTabsRail`/`Sidebar`/`WorkspacePill`), tab UI (`TabList`/`HorizontalTabs`/`TabFolderHeader`/`PinnedTabs`/`TabFavicon`), webview mounts (`TabWebViewHost`/`SplitPaneHost`, which measure rects and mount one native webview per visible pane leaf), and pages (`SettingsPage`, `HistoryPage`, `NewTabPage`, `DownloadsPage`).
- **Reload / stop / load progress**: `NavRow`'s reload button becomes an X while `Tab.loading` is set (`tab_stop` stops the engine load and clears the flag directly, so the toggle recovers even without a finish event; `tab_reload` uses the native reload so hung pages still respond). `LoadProgressBar` draws an accent strip along the URL pill's bottom edge from `wis-load-progress` events, emitted by `load_progress.rs`, a 100ms per-load poller of the engine's estimated progress (WKWebView `estimatedProgress` on macOS, WebKitGTK `estimated_load_progress` on Linux; WebView2 exposes no fraction, so Windows plays an indeterminate ramp off `Tab.loading`).
- **Hooks** (`src/hooks/`): `useBrowserState` + `useBrowserStateEvents` (fetch + invalidate the `BROWSER_STATE_KEY` query, `staleTime: Infinity`), `useTabWebviews` (webview lifecycle), `useThemeApply` (state to DOM), `useFolderTarget` (folder selection), `useWorkspaceBackground`, `useKeyActions`, plus one hook per overlay surface.
- **Lib** (`src/lib/`): pure helpers, notably `theme.ts` (`themeVars`), `tabMotion.ts`, `paneActive.ts`, `tabStripLayout.ts`, `design.ts`, `glass.ts`.
- **Bindings** (`src/bindings/`): typed IPC wrappers (`commands.ts`) and types mirroring `wis-core` (`types.ts`). Wrappers accept camelCase and translate to serde's wire format at the boundary.

State is immutable end to end: `wis-core` mutations are pure `with_*` builders returning a new value, and the frontend re-renders off refetched query snapshots rather than local mutation.

## Command palette sources

`lib/palette.ts` maps a query to ranked items; the surface renders sections in a fixed order and each source sorts its own. Sources are **synchronous**, so the two that need stored data take it as an argument and `PaletteSurface` does the fetching: bookmarks are pulled once per workspace (a bounded set, matched whole client-side), while history is searched in storage per query, held still for 120ms, and only from the second character. Both are scoped to the active workspace, matching the history page's own default. React Query holds the previous results while the next search runs, but `placeholderData` fires for any key without data of its own, disabled or not, so the surface also drops the entries outright below the two-character minimum.

Both sections rank title and URL separately, so either can be highlighted, and fall back to the URL as a title for a page that never reported one. History lifts a page by at most half its own match score for visit count, so a page visited often rises among comparable matches but never above a closer one. Each page section is capped at eight rows.

Recently-closed tabs get a section of their own, and opening the palette lists the last few. Rows reopen by row id rather than by URL, so the tab comes back with the session it was closed with and leaves the list. The list is refetched each time the palette opens, and again whenever a tab id disappears from the browser state while the panel is showing. It watches for a *vanished id*. The panel drops duplicate history rows. Filtering happens over the rows that actually **render**. A private window lists no closed tabs, since it records none and refuses to reopen one.

Section order runs tabs, recently closed, bookmarks, history, actions, settings, open: pages the user has already committed to first, most-committed downward, then commands, then the type-to-navigate fallback. Because the two new sections load asynchronously and splice in above the others, the keyboard cursor is anchored to a row's **identity** rather than its index.

## Page context menu

A document-start script (`page_menu.rs`) intercepts `contextmenu` in the page and posts what was under the cursor to `wisPageMenu`; `usePageMenu` converts the point and opens the `pagemenu` overlay; `PageMenuSurface` draws the menu. Rows are single existing commands, so nothing here needed new backend work.

The pieces that are load-bearing and non-obvious:

- **Suppression is the page's own `preventDefault`.** No engine exposes a usable native hook , so the listener is bubble-phase and returns early on `defaultPrevented`, which leaves sites with their own menus, the element picker and the pop-out overlay working.
- **Main frame only**, guarded in the script and re-checked in the Windows dispatcher. Handlers are reachable from any frame's script on macOS and Linux, which is tolerable because a report only ever *shows* a menu and every row still needs a deliberate click.
- **The zoom scale is measured**. Page CSS pixels are not window pixels once a site has its own zoom, so the chrome divides the pane rect it already measured by the page's reported `innerWidth`. Device pixel ratio is not involved.
- **The overlay is sized to the card, not the window**. Sized to the card, every right-click reaches the page or the chrome and re-opens the menu there. Dismissal is then the three signals the tab menu uses: Escape inside the surface, a left press in the chrome, and `wis-pane-focus` for a left press inside a page webview. That last one is delayed briefly **on Linux only**. Teardown deliberately does **not** hang off the DOM `blur` event. The OS-level window focus event is used instead. The surface acknowledges each open by sequence and the chrome tears the overlay down if none arrives, and the overlay is built once at startup. The chrome hands over the target but never *shows* the overlay.
- **Chrome screens get the same menu**. The launchpad, history, settings and the error pages are React inside the chrome webview, so no page script reaches them. `usePageMenu` also listens for `contextmenu` in the chrome and builds the target from the DOM directly. It skips anything already handled (the tab strip and the bookmarks menu prevent their own) and anything editable. Chrome targets omit the navigation rows, since there is no page webview behind them. Rows close the menu *before* doing their work. Rows that open something relative to the current pane switch to the right-clicked pane at that moment rather than when the menu opens. When a click has no link, image or selection to offer, the system menu is left alone rather than suppressed. Buttons that stand in for links opt in with `data-menu-url` (and `data-menu-label`).
- **Images and media are re-fetched, never taken from the page**. `page_image.rs` saves and copies through the workspace's loopback proxy, so DoH and the tracker rules apply. `is_public_web_url` screens the URL the page named *and every redirect hop*, because both commands hand their result to the user and a public host can answer 302 with a loopback address. The body streams under a 20 MB cap, the format comes from magic bytes rather than the URL or the content type, and the save-panel name uses the sniffed extension. Copy refuses SVG everywhere, and off macOS refuses anything but PNG, since the arboard path decodes only that. It also screens the *decoded* size: the dimensions are read from the header and refused above 64 megapixels before any decoder sees them. TLS is end to end through the proxy's CONNECT tunnel, so certificates are validated normally here. Media rows carry the element's *resolved* source, so a `blob:` URL from a streaming player is excluded. Saving media is not offered: downloads run through the engine's delegate, which has no fetch-this-URL entry point.
- **An overlay cannot raise a toast by itself**. `showToast` dispatches a DOM event, which never leaves the webview that fired it, so the surface emits `wis-toast-remote` and the chrome's `useToastOverlay` forwards it after matching the window label. The network rows report their own failures this way, falling back to a plain sentence when the error carries a whole URL.
- **A selection outlives the focus change, and is budgeted for the assistant**. Opening the menu focuses its own webview, and an unfocused document stops painting its selection. The ranges are redrawn through the highlight API, which paints over them without touching the DOM the way a wrapper element would. Selections stay **live**: `WebViewImpl::resignFirstResponder` calls `clearSelection()` on a page unless `maintainsInactiveSelection` is set. `webview_prefs::keep_inactive_selection` sets it through `WKPageSetMaintainsInactiveSelection` on the page ref, since `WKWebView` exposes no setter; both hops are SPI and both are guarded. It is armed once **each load has finished**, not at creation and not when one starts: measured, a navigation resets the flag, and arming it before a load or while one is in flight leaves the selection destroyed on blur exactly as before. Only arming it after a load holds, which is why a page that redirects on its way in behaved differently from one that did not. The engine then paints the selection in its unfocused grey and returns it to the accent when the pane is focused again.

  The stand-in is therefore only cosmetic, and covers only the moment the menu holds focus: it keeps the accent on screen where the engine would have shown grey, and WebKit's own selection takes over the instant the menu closes. Releasing is not just deleting the registry entry. Instead, blanking the rule while the ranges are still registered is what repaints them, and the entry is dropped a frame later under a generation guard, so a second right-click's repaint is not taken with it. While the stand-in is up it also carries `::selection{background-color:transparent}`. That rule suppresses the background only. Matching what the engine draws takes more than reading a colour, and `selection_color.rs` carries the two things that are easy to get wrong. **No engine paints the raw system colour**: `NSColor` hands back an opaque one and WebKit makes it translucent itself, so the module ports `RenderThemeMac::transformSelectionBackgroundColor`, meaning `blendWithWhite` for a light document and a flat 80% for a dark one. **Selected text usually keeps its own colour**: WebKit overrides the foreground only in a dark document and WebKitGTK never does, so a rule that always sets `color` turns every glyph in the selection one colour. Which branch applies is the **page's** to decide, since the engine reads the document's used `color-scheme`; `light-dark()` resolves through the same thing, so the rule states both branches and the page picks. The rule is written as two declaration blocks, the older syntax first, so an engine that cannot parse the second keeps the first. Only macOS is reproduced exactly: elsewhere the `Highlight` keyword supplies the hue with the engine's own alpha over it, and the foreground is set only on Windows, where Blink is the one engine that recolours. Link text and selections have separate budgets: 400 characters for a window, and 32000 for a selection. The search row trims back to what an engine would accept.
- **The assistant hand-off uses plain `after`, not `afterHere`**. The transcript is per workspace, so switching the active tab first would reset it out from under the question. `useAiAsk` drops payloads addressed to another window, and the panel latches on a rising sequence so one question is seeded once.
- **Composed rows are one transition**. `open_url_in_new_window` creates the workspace and its first tab in a single `mutate`, then spawns the window, rolling the workspace back if that fails. A private workspace is offered only the private variant, and no bookmark row, since it saves nothing.
- **View source shows the live DOM, not the served bytes**. Wis makes no second request: the fetch would carry none of the page's cookies, so a logged-in page would come back as its login wall. What is given up is the server's own formatting, comments a script removed, and pre-hydration markup; what is gained is that it always matches what is on screen, including the authenticated view. Capture goes over a `wisPageSource` channel mirroring `page_text.rs`, with the script evaluated on demand. It serializes a *clone* of the document so Wis's own injected nodes can be dropped without touching the live page. Reader mode omits the row. The capture is taken **before** the source tab is opened, and keyed by the page's own tab. It is held in Rust, capped, split into chunks so the page lays out only what is on screen, and dropped when the page's tab closes, so a source tab restored from a previous session will thus display nothing.
- **Inspect opens on the right-clicked node, on macOS**. The page script parks the node under the cursor on `window.__wisInspectTarget` as a `WeakRef`. That lives in Wis's content world, which the inspector cannot read, so `devtools.rs` first has the script mark the node with a `data-wis-inspect` attribute, and the inspector's reveal script finds the mark (through open shadow roots), removes it and reveals the node. No selector inspects a node: `_WKInspector` stops at `show`, `showConsole` and `showResources`. A fresh extension id is registered per invocation, since one that is still live is refused and the inspector drops its registrations when it closes. Both SPI entry points sit behind `respondsToSelector:` guards because messaging a selector a future WebKit dropped would raise. Any failure leaves the inspector open on the document. On Windows and Linux, Chromium's reveal is an event its front end receives rather than a method an embedder can call. WebView2's `inspectElement` command does not reveal the node on a cold DevTools open (Microsoft's WebView2Feedback #2371, still open), and WebKitGTK's public inspector API has nine functions, none of which reveal a node.
- **Inspect is a command the chrome calls, not the engine's own toggle**. `capabilities/tab-devtools.json` used to grant remote tab pages the devtools toggle. Deleting it and calling `Webview::open_devtools` from `devtools.rs` puts the inspector on Wis's own keymap. Thus, devtools work in every window rather than just `main`, and makes "a page can never call a Tauri command" true without exception. Webviews are built with `.devtools(!ephemeral)`, thereby disabling devtools in private tabs.
- **Save page asks the engine for an archive**. Every engine can already emit a complete single-file archive of the document it has loaded, which opens offline with its images, stylesheets and fonts. The format is the engine's own and therefore differs by platform: `createWebArchiveData` on macOS writes `.webarchive`, `save_to_file` with `SaveMode::Mhtml` on Linux and Chromium's `Page.captureSnapshot` on Windows both write `.mhtml`. The save panel runs *first* on every platform, because WebKitGTK writes straight to a destination and needs it up front.
- **Keyboard is bound to the window, not the card**. A disabled rows carry `aria-disabled`. `data-keybind-capture` goes on the document root so the chrome's own shortcuts do not fire underneath.

## Page-zoom chip

`ZoomIndicator` sits inside the address bar (`UrlBar`), after the input and before its other trailing controls, at their height. It reads the zoom for the active tab's host from settings (`lib/zoom.ts` mirrors the Rust lookup) and shows nothing while the page is at the default zoom. Hiding collapses its own `max-width` instead of unmounting, which gives it an exit as well as an entrance. Each character is keyed by its distance from the *end* plus its own value, so React remounts only the characters that changed: 110% to 120% moves the middle digit alone, 90% to 100% keeps the trailing `0%` still while the new hundreds digit and the changed tens digit arrive, and the per cent sign never moves. A remounted character replays one of two entrances, rising from below when the zoom went up and dropping from above when it went down; the direction is captured in a ref at mount. The global `motion-reduced` and `motion-off` tiers cover the animations without extra rules.

## Render performance

Refetch and re-render are coalesced so unrelated state churn stays cheap:

- Browser-state-changed refetches are coalesced per animation frame: `useBrowserStateEvents` guards a single `requestAnimationFrame` before invalidating `BROWSER_STATE_KEY`, so a burst of native events triggers one refetch.
- React-Query structural sharing returns the same reference on a no-op refetch, so a refetch that changes nothing re-renders nothing.
- `useBrowserStateSelector` (a React-Query `select`) skips re-renders on an unchanged slice; `useSettings` and `useActivePrivacyMode` subscribe to just their slice rather than the whole state.
- Always-mounted leaves are `React.memo`'d (e.g. `Brand`), so they hold steady through unrelated parent re-renders.
- The startup widget-favicon prefetch runs through a concurrency cap of 4 (`WidgetFavicon.tsx` `PREFETCH_CONCURRENCY`), deferred a few seconds after mount, so a cold-cache launch does not flood the favicon path.
- `open_widget_panel`'s main-thread surface hop is awaited on the blocking pool, so the calling task never blocks the async runtime on it.

## Settings page

`SettingsPage` is one scrolling column of `.sec` sections; the nav marks the section in view. Its search field (`SettingsSearch`) indexes the rendered `.row` elements (title, description, section heading) on each query, so it cannot drift from the page. `lib/settingsSearch.ts` keeps rows holding every word, titles starting with the query first. Matches replace the section list; picking one scrolls the row to the centre and flashes it. Segmented controls in rows never shrink, so descriptions wrap before pill labels do.

## Layout modes

`wis_core::layout::LayoutMode` has three variants: `SidebarLeft`, `SidebarRight`, `TopTabs`. `RailSide` (Left/Right) is the docked-controls edge; in `TopTabs` it decides which side the rail and its pinned circles anchor to, in sidebar layouts it mirrors the sidebar side. `Window` (the root host) picks the tree per mode.

- **Collapsible sidebar** (`Sidebar`) ends in a docked footer cluster (downloads, bookmarks, VPN, history, settings). It floats over the content area and is left transparent so it reveals the frame shadow rather than stacking a second dark layer. It auto-expands on hover, and a collapsed sidebar also expands when the cursor reaches the window's outermost edge column (document-level mousemove, since the window-resize handles sit on top of the in-aside hot strip and eat the first pixels).
- **Top-tabs** (`TopTabsRail` + `HorizontalTabs`) puts tabs in a horizontal strip with a docked rail of controls. The strip is corner-anchored opposite the rail: loose tabs and folder islands flow in one scrollable run (`.h-strip-run`, the strip itself never scrolls) while pinned circles stay anchored at all costs.
- **Top-tabs accordion limit**: `UserSettings.top_tabs_max_expanded_folders` (default 2, 0 = no limit; a segmented 1/2/3/No-limit control in Settings -> Layout, in the settings blob, no migration) caps how many folder islands stay expanded at once. Expanding one island past the limit collapses the least-recently-expanded island (session-scoped per-workspace recency, seeded in position order) and **sleeps** its members. `MEMBER_TAB_MAX` (150, or 120 compact, `lib/tabStripLayout.ts`) caps an expanded island's member-tab width, enforced only in the top-tabs UI (the sidebar tree is unrestricted).

## Workspaces, panes, pins, folders

- **Workspaces**: color-accented profiles, each with its own WebView data store, proxy, and privacy mode. One OS window per workspace is a hard invariant (`set_active_workspace` and `new_window` focus an existing owner window rather than duplicate). Store isolation is the WKWebView `data_store_identifier` on macOS and a per-workspace WebView2 user-data folder on Windows (`commands::workspace_webview_data_dir`).
- **Private browsing**: a private workspace is *ephemeral* (non-persistent data store), excluded from save and wiped on close. Its `selected_folder_id` and session state never touch disk. On macOS its tabs and widget panels share one store: `incognito(true)` would make wry create a store per webview, so `private_store` keeps one `nonPersistentDataStore` per private workspace and hands each webview a configuration carrying it (`with_webview_configuration`). The store is released when the workspace's window closes or the workspace is deleted, and WebKit drops its data with the last webview on it. Windows runs private webviews InPrivate in the workspace's ephemeral data folder (sharing across tabs unverified); Linux still isolates per webview.
- **Split panes**: a per-workspace binary `PaneNode` tree (`wis_core::pane`), `Leaf { tab }` or `Split { dir: SplitDir, first, second }`. Each leaf mounts its own native webview to a measured rect. `SplitPaneHost` handles resizable dividers and focused-leaf highlight; native click-to-focus (`pane_focus.rs`) routes keybinds to the focused leaf. Panes are in-window multitasking; new windows are for cross-workspace multitasking. Closing a pane's tab keeps the split when it can (`with_tab_closed_keeping_split`): the pane shows the window's most recent tab not already in a pane (`lib/tabMru.ts` sends its recent list with the close), else the nearest such tab in tab order, and only collapses when every other tab is already showing. Closing an unfocused pane leaves focus where it is.
- **Pinned tabs**: `Workspace.pinned_tab_ids` + `Tab.pinned`, kept in sync by `pin_tab`. Pinned tabs leave the normal list and render as a docked quick-access set in every layout (favicon grid in the sidebar, favicon circles at the rail-nearest end of the top strip). They never sit inside a folder (they sleep like any background tab). `reorderedWithPinned` reorders only the non-pinned subset and merges back so pinned slots survive in `tab_order`.
- **Tab folders**: `wis_core::tab_folder::TabFolder { id, name, accent, collapsed, position, icon }` group *live* tabs (distinct from bookmarks, which save URLs). `Workspace.tab_folders` + `Tab.folder_id`, mutually exclusive with pinned. The selected folder (theme-ring highlight) is the one place new tabs go: core moves it with the focused tab (`set_active_tab`, `close_tab`, pane focus, filing or pinning the active tab), and the shared `useFolderTarget` hook (`setTarget`) lets a folder header or bare-strip click override it, so a deselected folder yields loose tabs, including link, background-tab and bookmark opens. `+ New tab` always makes a loose top-level tab (`with_new_loose_tab`). Collapsing a folder **sleeps** its members immediately, bypassing the idle timer. `selected_folder_id` is not stored; load derives it from the active tab's folder so a foldered tab boots highlighted. Folders themselves persist in the JSON `tab_folders` column.
- **Workspace accents**: `UserSettings.custom_accent_palette` (shared across workspaces, in the settings blob) renders as the workspace popover accent grid's saved swatches, plus a dashed `+` square that spawns a tentative swatch via the `ColorPicker`. `Workspace.custom_accent` (a validated hex value, migration `M0016`) paints the workspace dot, and is cleared when a preset accent is picked (`with_custom_accent`).

## AI assistant panel

The assistant (`AiPanel`) is a chrome-side React surface docked beside the content frame. It renders as a sibling of `.kb-content` inside `.kb-main`, which flips to `flex-direction: row` under `.kb-main.has-ai`. Shrinking `.kb-content` shrinks `.kb-content-host`, and `TabWebViewHost`'s `ResizeObserver` on that element retiles the native webviews. The panel carries `position: relative` because `.kb-content` paints a `0 0 0 100vmax` chrome-frame shadow that would otherwise cover a static sibling.

- **Placement**: docked opposite the sidebar (right in `SidebarLeft`, left in `SidebarRight` and in top-tabs with a right rail), so the two chrome columns never crowd one edge.
- **Resize**: the drag grip sits on the panel's inner edge and reuses the split-pane divider protocol, dispatching `wis-pane-resize` (`detail: true`) for the duration. `TabWebViewHost` hides every native webview while that flag is set, so the pointer stays with the chrome for the whole drag and the webviews tile once on release. Width is chrome-local (`localStorage`, `wis-ai-panel-width`), clamped in `lib/ai.ts`.
- **Activation**: the panel exists only once the settings name somewhere to send to, which `aiActivated` in `lib/ai.ts` decides: a stored key activates either provider, and an OpenAI-compatible endpoint also activates on its base URL alone, since a local server (Ollama, LM Studio) authenticates nothing and `openai_request` omits the bearer header when no key is stored. A loopback base URL never even reads a stored key (`local_openai_base`), so a cloud key is not loaded for a local model. `useAiAvailable` probes `ai_key_present` and listens for `wis-ai-key-changed`, the event `ai_set_key`/`ai_clear_key` broadcast, so every window gains or loses the entry point without a restart. The platform arm is the `ai_assistant` entry in `lib/platformSupport.ts`, mirroring `ai_supported()` in `ai.rs`.
- **Session state**: `useAiChat` holds the transcript in memory for the window and nothing else. It is never persisted, and it is dropped when the active workspace changes so a private workspace's conversation cannot carry into another. The panel stays mounted after its first open and renders nothing while closed.
- **Routing**: a hosted provider goes through the workspace proxy like everything else, so the assistant inherits the workspace's privacy mode, blocking and upstream. A **loopback endpoint does not**: `ai_chat` parses the resolved URL and skips the proxy when `wis_network::is_loopback` says it points at this machine. There is nothing to route (the HTTPS-First upgrader already exempts loopback and the blocker allows it), and handing it to the workspace's upstream would push a local model's traffic off the device, to Tor, where it cannot arrive. An unparseable URL keeps the proxy, so the fallback is the private one, and a LAN address is not loopback and still routes normally. Page requests to loopback are unaffected and still go through the proxy: a page loaded over Tor probing local services is a different question from the app talking to a model the user installed.
- **Streaming**: `ai_chat` streams `StreamEvent`s over a `Channel`. Deltas are coalesced into one state update per animation frame, since a provider emits tokens far faster than the panel needs to repaint. A generation counter invalidates a superseded or stopped stream so a late delta is dropped, and Stop also calls `ai_cancel` with the request id the panel minted: `ai_chat` holds a cancel flag in `AppState.ai_cancels` behind an RAII guard and returns on the next chunk, dropping the response and closing the upstream connection, which is what actually stops the provider generating. Provider failures arrive as a terminal `error` event; a rejected command (no key, no model, no proxy) is caught on the same path and settles the same turn. A provider that stops at its output ceiling emits `StreamEvent::Truncated` (`finish_reason: "length"` on the OpenAI-compatible wire, `stop_reason: "max_tokens"` on Anthropic's `message_delta`), and the turn carries a visible "cut short" note instead of presenting the answer as complete. Generation itself carries **no deadline**, only the reach for the provider (`AI_CONNECT_TIMEOUT`). Ending a run is the user's call: the composer's send button becomes Stop for the whole in-flight window, reading and thinking included. Both the wait for the response head and the wait for each chunk sit in a `select!` against the cancel flag, so Stop lands during a slow first token too, and the reply is not merely muted: `ai_cancel` trips the flag, `ai_chat` returns, and dropping the response closes the upstream connection.
- **Reasoning**: a reasoning model streams its working before its answer, as `delta.reasoning` or `delta.reasoning_content` on the OpenAI-compatible wire and as a `thinking_delta` on Anthropic's, requested via the "Show reasoning" toggle (`AiSettings.show_reasoning`, off by default: thinking bills as output tokens and the adaptive config is rejected by older Claude models). With it on, the Anthropic body gains `thinking: {type: adaptive, display: summarized}` and `max_tokens` rises to at least 16000, since the cap covers reasoning and answer together. The OpenAI-compatible body therefore sends **no `max_tokens`**. Anthropic's Messages API requires the field, so that arm still sends it. `SseParser` normalises both wire spellings into `StreamEvent::Reasoning`, kept apart from `Delta`. The panel shows it as a shimmering "thinking" line that opens onto the live text on click, with an **Answer now** button beside it that cuts the thinking short: it cancels the in-flight stream via `ai_cancel` and restarts the same turn with `skip_reasoning` and a trailing "answer immediately" directive, and closes the tools. On the OpenAI-compatible wire that also appends the Qwen-family `/no_think` soft switch to the final user message in `chat_body`, honoured at the chat-template level by the most common local thinking models, and, for a loopback base URL only (`ChatRequest.local_server`), sends `reasoning_effort: "none"`, which Ollama honours for models that ignore `/no_think`; hosted APIs reject the field on models without reasoning. Anthropic keeps the turn's thinking settings (`thinking_for`), since current Claude models reject turning thinking off; closed tools and the directive, carried as a text block on the latest user turn, end the turn instead. Reasoning already streamed stays in the disclosure and the timer spans the restart. The line settles into a collapsed "thought for N seconds" disclosure (the window from first reasoning delta to first answer delta); with no reasoning the line is the same label without the disclosure, and it disappears once the answer starts. A chunk can carry both reasoning and answer text.
- **Markdown**: assistant answers render as markdown through a hand-rolled subset parser (`lib/markdown.ts`, pure: text in, a typed block tree out) mapped to escaped React elements (`AiMarkdown`). Anything the parser does not recognise falls through as plain text. Links never navigate, rather they render as buttons that open a new tab via `create_tab`, gated on `isWebUrl` (`lib/url.ts`, `URL.protocol` allowlist of http/https), with the destination host in the tooltip. Before opening, the click runs `ai_assess_link` (pure, over `wis_core::link_safety::assess_link` with the anchor text included): the panel is the only place that knows both a link's visible text and its href, the deceptive-text signal navguard's page-load check cannot see, so a link whose text reads as a different domain is held behind a confirm dialog naming the real host. Code blocks and tables scroll horizontally instead of wrapping; user turns stay plain text.
- **Page text**: sharing is an explicit action, either the Summarise button or the composer's include-page toggle (or a `read_tab` call, below, when local data is on), which resets after every send and whenever the page in view changes. `request_page_text` is answered by a broadcast `wis-page-text` event, so the panel takes a response only from the tab it asked. The text is fenced and labelled as data in the prompt, replayed from the transcript on follow-ups, and rendered through React escaping only. Every turn that carried page content says which host it came from.
- **Web access** (`AiSettings.web_access`, off by default): opting in declares two tools on the wire, `web_search` and `web_fetch` (`wis_core::ai::web_tool_definitions`), and `SseParser` reassembles the model's streamed `tool_calls` fragments into one `StreamEvent::ToolCalls` per round. The chrome runs the agent loop (`useAiChat`): it vets every call in pure code first (`planToolCalls` in `lib/ai.ts`: malformed arguments, hallucinated tool names and repeated queries become readable rejections, never requests), executes via `ai_web_search`/`ai_web_fetch`, appends the round to the wire and streams again, capped at `MAX_TOOL_ROUNDS` (4), after which `no_tools` withholds the declaration and a budget directive makes the model answer. Fetches are allowlisted to URLs a search returned or the user wrote; the Rust side re-checks `wis_network::is_public_web_url` regardless (entry and every redirect), so loopback, private ranges, link-local, CGNAT and credentialed URLs are unreachable however the model asks. `ai_fetch.rs` loads the page in a throwaway webview that is incognito, hidden before first paint, proxied through the calling window's workspace, refuses downloads, and carries no Tauri capabilities (`wis-fetch-` labels are granted nothing and are in the `terminate_window_pages` allowlist); a narrow `wisAiFetch` channel posts the extraction with the same script bytes on every platform (macOS `WKScriptMessageHandler`, the fetch-scoped `win_dispatch` receiver behind `AI_FETCH_SHIM` on Windows, a `UserContentManager` registration in `gtk_dispatch` on Linux), search results come from the no-JS DuckDuckGo page, and everything is torn down on every exit path inside a 20s ceiling. In the panel each round renders with the thinking row's flavour: the live spell closes into its duration when the calls arrive, a shimmering "using tool: web search / web fetch" row follows, and it settles into "search returned N results" / "fetched N sources" (or "search failed" / "fetch failed") with the query or URL and a truncated-but-real response behind the chevron. Answer now doubles as the loop breaker: it cancels whatever round is running and restarts with tools withheld.
- **Local data** (`AiSettings.local_data`, off by default): declares `list_tabs`, `read_tab`, `search_history` and `search_bookmarks` (`local_tool_definitions`) beside the web tools, never on an answer-now retry. The chrome runs them through the same loop (`runToolAction` in `useAiChat`), but every native command (`ai_local.rs`) re-checks the setting and takes the workspace from the calling window's binding, never from an argument and never by falling back to the active workspace, so a call the model was not offered, or one aimed at another workspace, fails. URLs reach the model without query, fragment or credentials (`redact_url`), since those carry login and reset tokens; matching still sees the whole URL. A round runs at most 8 calls (`MAX_CALLS_PER_ROUND`), the rest coming back as rejections. Once a turn has read local data, a web search waits for the user: its query is the one place that data could leave for a third party, for instance when injected page text steers the model. The same inline card that guards tab actions names the query; Skip tells the model the search was declined, and Stop, Answer now or a workspace change decline it too. Fetches need no approval, since they are already limited to search results and URLs the user wrote. Tabs carry 8-hex short ids resolved by unique prefix within that workspace. History search requires every word (one escaped `LIKE` on the longest word, then a filter, 20 hits); bookmark search filters the workspace's bookmarks and folder names in memory. `read_tab` resolves the tab natively (web pages only, awake only), then reads it like an attached page, capped at 8000 characters. A private workspace exposes only its own tabs, since it keeps no history or bookmarks.
- **Tab actions** (`AiSettings.tab_actions`, off by default, shown only while local data is on): declares `open_tabs`, `switch_tab`, `close_tabs` and `group_tabs` (`action_tool_definitions`). Every call waits for the user: the chrome previews the named tabs (`ai_preview_tabs`) or the URLs in their parsed form (`ai_preview_urls`) natively. It shows an inline card listing them with Cancel, Retry and Accept, and on Accept runs the action bound to what the card showed (full tab ids, parsed URLs). A preview that resolves after Stop, Answer now or a workspace change raises no card, and nothing runs once the turn is gone. Once the turn has read local data, the open card warns that an opened page receives its whole address; URLs with credentials or over 2048 characters are refused. Cancel tells the model not to propose it again; Retry asks for another attempt; both, and a declined search, settle as plain rows rather than failures. `ai_actions.rs` re-checks both settings and the window's workspace, opens only http(s) URLs (at most 5; one comes to the front, several open behind), closes through `close_tab` so tabs stay reopenable, and groups into a folder found by name or created with the sidebar's next accent, in one transition.
- **Anthropic tool use**: every tool works on both providers. `chat_body` declares them in Anthropic's form (`name`, `description`, `input_schema`) and keeps the declarations identical for the whole conversation, since current Claude models reject a changed tool list against earlier thinking signatures; the round cap and Answer now close them with `tool_choice: none` instead (`ChatRequest.tools_closed`). `SseParser` rebuilds each Anthropic tool-use turn block by block (thinking with its signature, redacted thinking, text, `tool_use` with its parsed input) and hands it over with the calls (`StreamEvent::ToolCalls.blocks`); the chat sends it back verbatim on the assistant turn (`content_blocks`), as the API requires, and a turn whose blocks fail the shape check is rebuilt from its text and calls. Each round's results go back together in one user message of `tool_result` blocks, and a later system directive (answer now, tool budget) rides the latest user turn as a text block after them, since only the leading system prompt has a top-level place.
- **Research mode** (`lib/research.ts`, composer toggle shown only while web access is on): `send(question, page, { research: true })` runs a fixed pipeline. A non-streamed planning request (`planWire`, Stop cancels it, complete only at its own `done` event) yields two or three queries (`parseQueries`, which drops reasoning a server left in the reply around `</think>`, falling back to the question). It runs with `skip_reasoning` and the searches run in parallel. `pickSources` takes each query's results by rank in turn, once per page and at most two per registrable site (`siteOf`, the `registrable_domain` heuristic), up to `RESEARCH_CANDIDATES` (8). `readEnough` reads them three at a time through `ai_web_fetch` at a raised `RESEARCH_READ_CHARS` (20k) limit, judges them in rank order (so of two copies the better-ranked one stays), skips thin pages (under 150 words, counted with `Intl.Segmenter` so scripts without spaces count too) and copies (most text shared, or a matching title with some text shared, since generic titles recur across sites), and stops once `RESEARCH_PAGES` (6) are kept. The page script keeps line breaks, so `excerpt` can keep the passages that best match the question's and queries' content words (`researchTerms`), in page order with gaps marked, within `RESEARCH_PAGE_TOKENS` (1000) per page. `estimateTokens` counts a quarter token per character and three quarters in scripts without spaces, measured against Qwen's tokenizer, so six pages stay near 6k tokens. Settings tell OpenAI-compatible users that research needs a 16k context. The write-up then streams on the normal path with tools closed: the sources are fenced as numbered data in the user turn between two statements of the question (`researchContent`; marker-like lines in page text and titles lose their `=`, so a page cannot close the fence) and the system prompt gains the citing rules (`withResearch`). Progress shows as tool rows (plan, one per search, one read group that gains a row as each read starts) and Answer now stays hidden until the write-up starts. The answer's `[n]` within range render as buttons (`splitCitations` through a context in `AiMarkdown`) that scroll to and flash the numbered source list under the turn; a source opens through the same link check as any answer link. Follow-ups replay only the question and answer, not the source text.

## Icons

Folders and workspaces carry an icon rendered inside their color dot (`set_tab_folder_icon` / `set_workspace_icon`). Encoded as a compact string (`glyph:<name>` | `glyph-fill:<name>` | `emoji:<char>`), validated by pure `wis_core::icon::parse_icon_ref` at the command boundary; glyph names are charset-checked in core and resolved in the chrome (`src/lib/iconGlyphs.tsx`, Lucide-derived wire+fill shapes), unknown names fall back to the plain dot. No migration: `TabFolder.icon` rides the JSON `tab_folders` column and `Workspace.icon` repurposes an existing unused column. Glyphs tint with `currentColor`; emoji render as-is. Picked via the shared `IconPicker` (Line/Fill/Emoji tabs + None reset).

## URL-bar suggestions

An overlay dropdown (`useUrlbarSuggest` + `lib/urlbarSuggest.ts`): recent searches, history-ranked site recommendations, inline base-website completion, favicons. Because native tab webviews composite above the chrome, this is a separate overlay webview positioned natively, not HTML in the chrome. Search resolution lives in `lib/url.ts` (`resolveInput`): keyword triggers (`kw query`; custom engines first, then optional built-in keyword assignments, empty by default) are checked before the URL/host heuristics, then the active engine (the custom engine marked `is_default`, else the built-in DuckDuckGo/Google/Bing choice) builds the query URL. An address needs a dot, except `localhost`, a bracketed IPv6 literal, or a name with a port (`devbox:8080`). Loopback (`localhost`, `*.localhost`, `127.x`, `[::1]`) opens over `http://`; everything else gets `https://`. Engines are managed in Settings > Search (`SearchSection`); the pure model and boundary sanitizer live in `wis_core::search` (`sanitize_search_engines`: http(s)-only `{searchTerms}` templates, unique lowercase keywords, one default, capped). The command palette's type-to-navigate row shares the same resolution. On Windows the close path supersedes any in-flight refresh (bumps a request id) so a late `showUnderBar` can never re-show the just-closed overlay over the content column. Click-away closes through two fallbacks beyond the input's own blur (which never fires when OS focus jumps to a tab webview): a window `blur` listener funnels into the same delayed close (overlay row clicks cancel it via the pick event), and a capture-phase outside `pointerdown` in the chrome closes immediately. The same hook also powers the **launchpad omnisearch** (`NewTabPage`, anchored to its form so the dropdown takes that width): same suggestion rows, engine resolution, and search recording as the top bar; the dropdown opens on click / Cmd+L / typing, not on the mount autofocus. Open-tab resolution + switching is shared via `useOpenTabActions`.

## Launchpad + homepage

The new-tab page (`NewTabPage`) is configurable via `wis_core::new_tab`: `NewTabTarget`, `ShortcutTile`, with boundary sanitizers `sanitize_homepage` / `sanitize_shortcuts`. Quick-access tiles and history rows honor the chrome middle-click contract (`onAuxClick` -> `create_background_tab`, opening a background tab and staying on the page). The launchpad also hosts the per-workspace background: it reads `--wp-grad` and the wallpaper layers straight off `<body>`, so a background themes the page with zero component changes.

## Backgrounds

Per-workspace, `Workspace.background: Option<Background>` (`wis_core::background`), persisted as JSON; ephemeral workspaces keep it in memory only. Each mode's last configuration persists in `Workspace.background_drafts` so switching modes restores what the user built in each.

- **Gradient**: `GradientSpec` (angle + 2..8 hex stops, validated at the IPC boundary), edited live from `BackgroundEditor` (angle capped 0..=180 since larger angles mirror smaller ones, per-stop `ColorPicker` in `controls.tsx`). Rendering overrides the `--wp-grad` token on `<body>` via `useWorkspaceBackground`.
- **Image/GIF**: `import_wallpaper` validates by magic bytes only (png/jpeg/gif/webp), caps at 20 MB, stores content-addressed at `<app_data>/wallpapers/<sha256>.<ext>`. Served through `wis-asset://wallpaper/<hash>` (answers only `main`/`overlay-*` labels, hash strictly 64 hex chars so requests cannot escape the store). `Background::Image { asset, fit, dim, blur }`: fit maps to cover/contain/tile, blur 0..=40 px blurs the wallpaper without content, dim 0..=80% layers a black overlay. The launchpad paints it as one shared canvas spanning the whole content host, so split panes reveal contiguous slices of a single wallpaper with blur seams aligned.

## Theming

`useThemeApply` is the single sink that mirrors settings onto the DOM (verified in `hooks/useThemeApply.ts`):

- Theme mode: `data-mode` on `<body>` (Light/Dark/System). Also pushed to web content (`apply_tab_appearance`): macOS `NSAppearance` DarkAqua/Aqua, Windows WebView2 `PreferredColorScheme` (per-profile), so a page's `prefers-color-scheme` matches the in-app theme.
- Accent: `data-accent`; a custom theme's inline `--primary-50..900` vars beat the `[data-accent]`/`[data-mode]` rules.
- A custom theme left at the defaults looks exactly like the built-in one: `themeVars` emits tokens.css's own hand-tuned primary scale for the default accent and its subtle backgrounds for the default neutrals. Edited tokens derive the rest. `tests/lib/theme.test.mjs` reads tokens.css to hold the defaults to it.
- Design (`wis_core::design::ChromeDesign`): `data-corners` and `data-glass` drive `--radius-scale` / `--glass-scale` multipliers in `tokens.css`; `data-tab-shape`, `data-folder-style`, `data-tab-indicator`, `data-density`, `data-close-btn` select `window.css` variant blocks; `--sb-w` is set inline. Glass is scoped: `glass-on` is the master toggle, gated per surface by `glass-chrome`/`glass-menus`/`glass-tabs`.
- **Custom themes** (`ThemesSection`): `CustomTheme` carries light+dark `ModeTokens` (accent + bg/surface/raised/chrome/content/text/secondary/border, all validated hex via `wis_core::theme`); the accent expands into the whole scale at apply time (`src/lib/theme.ts::themeVars`, pure mixes toward white/black). `set_active_theme` injects the vars inline, so the chrome re-themes and reverts to presets with zero component changes. Sharing moves versioned `.wistheme` JSON (import size-caps, validates the full structure, rejects newer versions, re-mints the id so a shared theme cannot collide) or portable `wis-theme:<base64>` clipboard codes.

## Motion

Central motion tokens in `tokens.css` (`--dur-fast/med/slow`, `--ease-standard`, springy `--ease-emphasized`, `--ease-exit`) back every chrome transition; the scattered hardcoded durations were folded into them. `UserSettings.motion` (`MotionLevel`: Full/Reduced/Off) maps to body classes in `useThemeApply`: **Reduced** keeps durations but flattens `--ease-emphasized` to standard (no overshoot), **Off** zeroes transition/animation durations, and OS `prefers-reduced-motion` caps Full at Reduced live.

- **Drag-reorder** (`lib/tabMotion.ts`): the source hides under a floating ghost while siblings **live-part** one slot around the insertion point (`body.is-tab-dragging`). Hit-testing measures **parting-free** rects (`layoutRect` = live rect minus transform), else the drop boundary chases the pointer. Reorders and folder assignment apply optimistically (`patchTabOrder`/`patchFolderOrder`), then the drop glides from the ghost into its slot with a settle pop (WAAPI, dropped on Reduced/Off).
- **Closing a tab** is a FLIP glide, not a collapsing slot. The closing tab leaves the sizing inputs and goes `display: none` on the close frame (slot and gap gone at once); survivors snapshot their rects (`captureFlip`) and animate from old to new with `translateX` + `scaleX` (position and width in lockstep). Closing the active tab predicts the promotion locally (`lib/paneActive.ts`, a pure mirror of `with_tab_removed` then `with_pane_after_removed`) so it sizes right before the refetch. Triggered synchronously over a same-tick DOM event, deduped per id; a new close cancels the in-flight FLIP.
- **Native surfaces** (panes, widget panels, Peek) animate by stepping webview bounds per frame over IPC; a live page is never resized (reflow-per-frame reads as jank). Split entrances glide a leaf's flex-grow from zero while the other webviews tuck away (`.is-entering`); removals keep painting the outgoing tree and glide the closing subtree shut (`.is-exiting`) before the committed tree reveals.
- Active-tab markers are single sliding bars measured against the list root (`.kb-active-bar`, `.kb-settings-nav-ind`), not per-row pseudo-elements. Workspace switches slide the tab list/strip in from the new workspace's relative side (`workspaceSlideIn`, imperative WAAPI, no remount).
