# Webviews, Windows & Overlays

This guide elaborates on WIS.md. If anything here conflicts, WIS.md wins.

## Compositing model

Native tab webviews (`tab-<uuid>`) composite **above** the chrome webview, so HTML chrome cannot draw on top of a page.

- Any floating UI over a page (find bar, palette, URL-bar suggestions, clear-data dialog, vault menu, pane-split menu, Peek, window picker) cannot be plain chrome DOM. It is a separate **overlay webview**, positioned natively.
- Stacking is tabs < widget panels < overlays. macOS uses `addSubview:` re-add order (`overlay.rs::promote_overlays_to_front`, `panels.rs::promote_panels_to_front`); Windows uses `win_webview2::promote_to_front` (`SetWindowPos(HWND_TOP)`), since HWND z-order is creation order and wry repositions with `SWP_NOZORDER`.
- Both promote helpers filter by the caller's **per-window** label prefix. Subview/HWND order is per `NSWindow`/frame, so restacking another window's still-loading views is pointless and crash-prone.
- Every webview is built with the wry drag-drop handler off: chrome via `dragDropEnabled: false` (`tauri.conf.json`) and `windows.rs`, overlays, tabs, widget panels and Peek via `disable_drag_drop_handler()`. Nothing in Wis consumes Tauri drag-drop events; wry still upgrades a None drag operation to Copy on macOS (cursor badge only). Hidden child webviews (idle overlays, background tabs, dismissed panels) are also parked off-window while hidden and moved back on show, keeping their logical bounds (eighth vendored wry patch), because AppKit resolves a drag destination from the frontmost view under the cursor without checking the hidden flag.

## Overlay webviews

Overlays are **per-window** and routed by URL, not label.

- Label is `overlay-<window>-<name>`, so each OS window owns its own find bar/palette. `overlay.rs::ensure_overlay` builds it from the calling window; `set_overlay_bounds` / `size_overlay` / `hide_overlay` resolve it the same way.
- The chrome drives one through `useOverlay(name)`, whose `{ show, hide }` is stable for the name. It used to be a fresh object every render, so the hooks listing it re-subscribed their Tauri listeners on every render of their host and could drop events in the gap (it took out the signup offer once).
- `main.tsx` picks the surface from the **URL query** (`index.html?surface=<name>`), not the label, so the window prefix never affects routing. Chrome loads `index.html` with no query and renders the full App; `overlay/OverlayRoot.tsx` dispatches to a surface in `overlay/surfaces/`.
- A surface focuses itself with `focus_self` (calling webview becomes first responder, no label), so it works on any window.
- The `wis-asset` wallpaper protocol answers chrome surfaces only (`main`, `win-*`, any `overlay-*`), so tab/widget pages get 403.

## One window per workspace

The browser is **one OS window per workspace**; in-window multitasking is the pane split, never a second window over the same workspace (two windows would conflict its `tab-*` webviews).

- `windows.rs::spawn_window` builds a `win-<uuid>` `WebviewWindow` loading the same chrome bundle as `main`, binding its label to the workspace in `AppState::window_workspaces` **before** the build so the chrome's first `get_browser_state` resolves correctly. The bundle is window-agnostic: it reads its own label via `getCurrentWindow()` and routes tab/overlay/peek/widget creation to that window.
- **Invariant enforcement**: `set_active_workspace` and `new_window` resolve `window_for_workspace(id)` first; if another window already shows that workspace they **focus that window** (`focus_window`: deminiaturize + `set_focus`) instead of duplicating it. On collision `set_active_workspace` is a no-op and the caller's `invalidateQueries` refetch self-heals; `new_window` returns the owner's label.
- A secondary window's bind clears on the `Destroyed` event, freeing the workspace back into the picker.
- **New Window** opens the free-workspace picker (`WindowPickerSurface` via `useWindowPickerOverlay`), listing `free_workspaces` plus a *New empty workspace* row. **New Private Window** skips the picker and opens over a fresh ephemeral workspace. Cmd+Shift+N is **Toggle Private Workspace**, which switches this window to its private workspace (creating one with a new tab when there is none) and, from a private workspace, back to the last regular one the window showed.
- **Move to New Window** / **Move to workspace** (tab menu): `move_tab_to_new_window` creates a fresh workspace (private when the source is), recreates the tab atomically (`with_new_loose_tab` + `with_tab_closed`), then `spawn_window`s it. History/scroll survive the webview rebuild: the command captures the source webview's `interactionState` into `AppState::pending_restore_states` keyed by the new tab id, which `commands/webview.rs::create_tab_webview` replays.

## Session and geometry restore

The windowed set is persisted **continuously**, not at exit.

- Every `set_window_workspace` / `clear_window_workspace` writes the snapshot via `Storage::save_windowed_workspaces` (a `meta` key that, unlike document tables, survives `save_state`'s `clear_all`). Continuous writes survive a non-graceful exit; a `make dev` stop never fires `RunEvent::ExitRequested`.
- Startup seeds `window_workspaces` directly (not via the setter) so the set is intact when `main` calls `restore_session_windows` once (guarded by `AppState::session_restored`), which `spawn_window`s each saved workspace. Deleted/ephemeral workspaces resolve to nothing and are skipped, so private windows never restore.
- Geometry is persisted **per workspace, not per label** (`win-<uuid>` labels are fresh each run). `record_window_geometry` snapshots position/size on `Moved`/`Resized` into `AppState::window_geometry` under a `window_geometry` meta key, debounced by `geometry_gen`. `spawn_window` applies it at build time (no jump); `main` is declared `visible: false` and positioned-then-shown in `setup`.

## Main-thread AppKit marshaling

Every AppKit call reached from a command must run on the main thread; commands run on tokio workers and off-main AppKit crashes non-deterministically.

- The window is built (and its shadow disabled) via `run_on_main_thread`. This bites anything touching Cocoa directly rather than through a Tauri/`with_webview` handle (which already hops to the event loop). Example: `set_dock_icon`'s `setApplicationIconImage:` drives `-[NSDockTile display]` -> CoreGraphics, so it must be wrapped (a new private window calls it with `"closed"` on mount, else it segfaults on the worker).
- The Dock icon is process-global but the model is one workspace per window, so `useDockIcon` drives it only while its window holds focus.
- **App-wide broadcasts must be focus-scoped**: `wis-keyaction` and `wis-peek-open` use `app.emit`, which reaches every window and always matches a default-target listener, so ungated they would open a tab in every window at once. Each listener gates on `lib/windowFocus.ts::isWindowFocused()`. Same gotcha for `Webview.getAll()`: `useTabWebviews` cleanup filters by `wv.window.label` before closing leftover `tab-*` webviews, else an opening window would kill a sibling's live tabs.

## Engine-popup routing

Tab webviews route engine new-window requests by intent in `commands/webview.rs` `on_new_window`, delegating the discriminator to `popup_chrome.rs`.

- `wants_popup` is true when the request **declares geometry** (`window.open` with width/height/left/top, the OAuth-consent shape) or targets `about:blank`. That is **Allowed** as a native wry window using the opener's WKWebView config, sharing the workspace session + proxy and keeping the `window.opener` link OAuth needs.
- A plain navigation (`target=_blank`, featureless `window.open`) to the opener's **own site** (`same_site`, an eTLD+1 approximation with a small ccSLD table, so `mail.google.com` and `accounts.google.com` are one site) is Denied and navigated **in the current tab**. A **cross-site** plain navigation is Denied and re-emitted as `wis-open-in-tab-fg` (`link_open::OPEN_TAB_FOREGROUND_EVENT`), which the focused window opens as a foreground tab.
- Widget panels (`widget_panel.rs`) share this routing minus the in-place branch, and add a page-script rule for plain clicks: cross-site links post `wisOpenInTabFg` (foreground tab), same-site links stay in the panel. Security: the allowed popup is a bare wry webview with **no Tauri capability**, so the local-vs-remote boundary holds.

## macOS popup shims

The popup is built inside wry (no shell handle, vendor unpatched), so decorations are added app-side by `popup_chrome::ensure_running`, macOS-only.

- `window.close()`: wry gives the popup no `UIDelegate`, so WebKit's `webViewDidClose:` would be dropped. The poll assigns a `WisPopupUiDelegate` that closes a window only when the webview **is** the window's content view (the popup shape), so a browser window can never be closed by page script.
- File `<input>`: the same delegate implements `runOpenPanelWithParameters:`, so browse-from-computer in a popped-out compose window opens an `NSOpenPanel`. Without it WebKit no-ops the picker. Windows/Linux runtimes render the dialog themselves, so this shim is macOS-only.
- **Read-only address bar**: the decoration appears on the next main-loop tick (titlebar accessory with the window, no content jump), a read-only URL field plus scheme glyph (lock for https, warning for http), **seeded with the target URL** because the popup's `WKWebView` reports `about:blank` until it navigates. A refresh poll tracks later redirects and self-stops (`STOP_AFTER_MISSES`) once every popup closes.
- Detection is precise: child webviews (tabs, panels, overlays, Peek) are subviews of the main window, and every Tauri-managed window is excluded via `ns_window()`, leaving only engine `window.open` popups.

## Cmd / middle-click open-in-tab

Cmd/middle-click on a link must open a new **tab**, not a popup, so it is intercepted before `on_new_window` sees it.

- `link_open::page_script` intercepts `Cmd`/`Ctrl`+click and middle-click on `<a href>` (Opt+click stays Peek's), `preventDefault`s WebKit's open-in-new-window, and posts the href to the `wisOpenInTab` handler, which emits `wis-open-in-tab` (widget panels also bake it, plus `panel_page_script` posting cross-site plain clicks to `wisOpenInTabFg`; one `OpenInTabHandler` serves both names and picks the event from `message.name`). The focused window opens a **background** tab (`create_background_tab` -> `with_new_background_tab`), placed right after the opener (the active tab) and behind any tabs already opened from it, so a run of opens keeps link order (`with_new_related_tab`, which appends instead when the new tab files into a different folder than the active one). Foreground opens (`wis-open-in-tab-fg`) go through `create_related_tab` with the same placement, while Cmd+T, bookmarks and the launchpad keep appending. Real `window.open` / `target=_blank` (untouched by the script) still flow through `on_new_window`.
- **Chrome surfaces mirror the contract** (cross-platform, `onAuxClick` -> `create_background_tab`): launchpad tiles and history rows stay on the page; bookmarks-menu rows keep the menu up so several open in a row. Every chrome middle-click target also `preventDefault`s the middle-button **mousedown** (Chromium engages pan/autoscroll then, too early for `auxclick`-time preventDefault). Palette and URL-bar suggestion rows are excluded.

## Hover guard

An overlaying webview or floating window over a tab does not stop the covered tab `WKWebView` from updating CSS `:hover`, so `hover_guard.rs` suppresses it (macOS).

- Each covering surface carries a tracking area; while the cursor is over it, the covered window's tab pages get a scoped stylesheet disabling `pointer-events`, removed on leave. The areas are active always, not only in the key window: a leave lost while the window was not key, as across a sleep, left every tab ignoring clicks until it reloaded. A system wake also lifts every guard (`wake.rs`).
- Scope: the widget panel (same-window child, `install_panel_hover_guard`), the video popout window (suppresses the origin window's other tabs), and engine `window.open` popups (free-floating, suppress **every** window's tabs via `arm_popup_suppression`).

## Capability boundary and window styling

The security boundary is **local vs remote content**, not just the window.

- The `default` capability has no `remote` block, so it applies only to local app webviews (chrome + `overlay-*`, loading bundled `index.html`) on its glob `["main", "win-*"]`. Tab pages and the Peek preview (`peek-page-<window>`) load remote `http(s)` and match no command-granting capability, with no exception.
- **The press that changes panes never destroys a selection (macOS)**. `pane_focus.rs`'s mouse monitor spots a left press landing in a tab webview while a *different* one holds first responder, takes focus itself, and arms that pane for one press. The page then takes the default off that press, but only if it currently holds a non-collapsed selection: `preventDefault` on `mousedown` suppresses the caret and the collapse while leaving `click` to fire, so a link or button under it still works first time. With nothing selected the press is left entirely alone. The residual cost is confined to the case that can be seen: with a selection showing, the first drag in that pane will not start a new one.
- **Each tab webview sits in its own pane-sized container (macOS)**. wry adds child webviews straight to the window's content view, so a tab's superview was the whole window. WebKit reads that superview in two places and assumes it is the page's own area: the attached inspector lays the inspected view out across `superview.bounds`, and element fullscreen keys its placeholder on the view's origin within its superview. `pane_container.rs` wraps each tab in a `WisPaneContainer`, inserted where the webview already sat. A container declines an interaction when it has nothing to show for. Its `hitTest:` returns nil when the webview inside is hidden, letting the press fall through. `set_tab_webview_bounds` moves the container while the webview fills it, which makes both assumptions true: the inspector splits inside its pane, and fullscreen measures zero. The corner radius moves onto the container so it survives WebKit resizing the webview inside it. A bounds push is silent while the webview is not in its container. Wrapping is self-healing on every bounds push, because the video popout reparents the webview to its own window and Tauri hands it back to the content view. The radius is set on the webview as well as the container.
- **Private tabs are not inspectable**. Webviews are built with `.devtools(!ephemeral)`. The Inspect row is omitted there as well.
- Chrome floats over an OS-vibrancy frame: `--content-bg` inside the periwinkle border (transparent in glass), darker `--chrome-bar` / `--chrome-bar-glass` for the frame, painted as a `box-shadow` spread on `.kb-content` (clipped by `.kb-main { overflow: hidden }`). Split panes reuse this as a cut-out: `.pane-surface` is a transparent rounded window whose **outset** `box-shadow` draws the pane ring then floods the outside with frame tone. An outset shadow never paints inside its box, so the page stays transparent. Off macOS the ring is **square** (`body:not([data-platform='macos'])`): native corner rounding (`set_webview_corner_radius`) is macOS-only, so a rounded ring would disconnect at a square WebView2 corner.
- Per-platform frame: macOS `titleBarStyle: Overlay` + `hiddenTitle: true` (native traffic lights), chrome shadow disabled to avoid a glass flash on navigation. Linux `decorations: false` + `transparent: true`, re-asserted post-realize for GNOME/Mutter CSD. Windows glass is **Mica** on Windows 11 (`windows::chrome_window_effects()` returns `WindowEffect::Mica`, applied to secondary windows at build and to `main` via `set_effects` before reveal, since `hudWindow` is macOS-only); Windows 10 gets none. Secondary windows mirror `main`'s glass via `chrome_window_effects()` plus the Overlay title bar and disabled shadow.

## Extensions (macOS 15.4+)

`extensions/` hosts WebExtensions through WebKit's `WKWebExtensionController`. Unused costs nothing: with no extension installed, tabs keep their old creation path.

- **Install**: Settings > Extensions opens an `NSOpenPanel` for a folder or `.zip` (`install::ask_source`). The files are copied or unzipped into `extensions/staging/<token>` (`stage.rs`: 256 MB and 10 000 files and folders at most, 24 levels deep, links refused and files opened with `O_NOFOLLOW`, zip entries kept inside through `enclosed_name`, Finder's `__MACOSX` and `._` litter skipped), the manifest may sit one folder down, and WebKit reads the staged copy. The review (`wis_core::extensions::review`) lists what it can do from WebKit's `requestedPermissions` and `allRequestedMatchPatterns`, the manifest permissions WebKit dropped, and a warning from 10 000 blocking rules on by default. Installing moves the folder to `extensions/<id>` under a fresh id and adds it to `UserSettings.extensions`, which only the extension commands change; removing unloads it everywhere, then deletes its files.
- **Which extensions run where**: `InstalledExtension.disabled_in` lists the regular workspaces it is switched off in, and `allow_private` lets it into private workspaces, whose ids do not outlive them (`wis_core::extensions::runs_in`, `wanted_in`). Every change goes through `install::change`, which edits the list in one state transition and gets back the one it replaced; the pages rebuilt are those of workspaces whose running set differs between the two.
- **One host per workspace** (`host.rs`, main thread): for a regular workspace, a controller with a persistent configuration whose identifier derives from the workspace, so extension storage is per workspace. A private workspace's host takes its in-memory store from `private_store::store_for`, a non-persistent controller configuration, and contexts with `hasAccessToPrivateData`. The workspace's store, the one wry opens for `data_store_identifier`, goes on both the controller's `defaultWebsiteDataStore` and its `webViewConfiguration`, and gets the workspace proxy before any extension loads. With only `defaultWebsiteDataStore`, background traffic was measured going around the proxy; wry sets the proxy only when a tab is built, and a background worker can run before any tab exists. A store whose proxy cannot be set gets no host. Contexts keep the extension id as their unique identifier and are granted the permissions the review listed; their sites come from their site access.
- **Tabs**: a regular workspace's tab is built from a configuration carrying the store and controller (`with_extensions`), once the installed extensions have loaded (5 s at most). Listing the toolbar's actions starts the host the same way (`ensure_host`, session cookies restored first). Its webview is then registered with the controller through a `WKWebExtensionTab` adapter, and the workspace through a `WKWebExtensionWindow` one; without them content scripts and blocking rules still run but messaging to the background fails. `terminate_page` unregisters a tab. WebKit lists no tabs while the window's active tab is one it does not know, so the host reports the state's active tab once it is registered and the first registered tab until then; `mutate_with` passes active-tab changes on while a host is live. A host lasts as long as its workspace's window, released with `private_store`'s stores when the window closes or the workspace is deleted, so sleeping the last awake tab does not restart every extension; the extension list an install or removal leaves wins over one a tab read earlier, and a load finishing for a released host is dropped. Canvas tabs and private workspaces get no controller. Extension errors open the tab without extensions rather than failing it.
- **Open pages follow a change**: after an install or removal, `wis-extensions-changed` names the web tabs of regular workspaces (`rebuild_targets`), and each window puts the ones it holds through the sleep path: their session (history, scroll, forms) is saved, the webview closed and, for an on-screen tab, rebuilt at once from the current set; the rest wake with it. A reload would not do: a tab built before the first install has no controller, and unloading leaves what an extension already did to a page. Popped-out and audible tabs are left alone.
- **Tab events and cleanup**: title changes and page loads reach the controller through `didChangeTabProperties` (title, then loading and URL), so `tabs.onUpdated` fires. A removal clears the stored data of every extension no longer installed from each regular workspace's storage: WebKit lists the data records of extensions that are not loaded, so a workspace without a window gets a short-lived controller on its storage identifier. Deleting a regular workspace clears its extension data the same way, when any extension was ever installed, and the launch sweeps extension folders no longer installed. A host still ends only with its window: after a workspace switch the old workspace's tabs live on hidden in that window, and releasing its host would leave them on an untracked controller.
- **Toolbar** (`actions.rs`, `ExtensionsButton`, `ExtensionsMenuSurface`): the address bar shows a puzzle button once any extension is installed. It opens the `extmenu` overlay, placed under the button by `lib/extensionsMenu.ts` and fed the button's rectangle and `extension_actions`: each running extension's action for the active tab, with its label, badge, enabled state, whether it has options, and its icon as a PNG data URL. Running one (`extension_run`) keeps the rectangle and the window's content view as the anchor and calls `performActionForTab`; the controller delegate's `presentPopupForAction` then shows WebKit's own `popupPopover`, which sizes itself to the popup and floats in its own window above the tab webviews. Its frame takes Wis's theme, as tabs do. WebKit makes it semi-transient, so AppKit closes it on the mouse-down of any click in the window, the puzzle button's included; `actions.rs` records when it closed (`NSPopoverDidCloseNotification`), and the button asks `extension_dismiss_popup` first, so a click that closed a popup, or finds one open, does not also open the menu. Options pages, from the menu or an extension's `openOptionsPage`, open in a native window built on the extension's `webViewConfiguration`, one per extension, outside Wis's tabs and capabilities.
- **Runtime permissions** (`prompts.rs`, `grants.rs`, `ExtensionPrompt`): `permissions.request` reaches the controller delegate as up to two questions in one turn, one for permissions and one for match patterns, and a CORS failure in an extension page as a question about URLs. `prompts.rs` keeps their completion blocks and asks once per extension on the next turn of the main queue, all or nothing. A request whose wording (`wis_core::extension_access::request_abilities`) is empty, such as `alarms` alone, is allowed without asking; otherwise any open popup closes and `wis-extension-permission-request` goes out with the workspace id. The window showing that workspace puts the question in the `extmenu` overlay under the extensions button, sized to what the surface measures. WebKit denies after two minutes, and a later answer counts as a denial. WebKit keeps no grants across launches, so allowed items go to `InstalledExtension.granted` through `install::change`, except in a private workspace, whose grants end with it. `grants.rs` grants them to each context before it loads, and when the list changes grants the new ones and clears the removed ones (status `Unknown`) in every loaded context. Clearing a site also clears the narrower sites it covers, so the manifest's sites and the remaining grants are granted again after it. Only items the extension still declares as optional, or patterns its declared ones cover, are granted. An extension's own `permissions.remove` posts WebKit's removal notifications, which drop those items from the settings. Settings lists what each extension was allowed in words, with Take back.
- **Site access** (`grants.rs`, `actions::site_state`): `InstalledExtension.site_access` is `all`, the default, or `allowed`, with `allowed_sites` holding exact hosts granted as `*://host/*`. A context's sites come from `grants::Access`: the manifest's requested patterns for `all`, the allowed hosts otherwise, plus what it was allowed while running. An allowed host is granted only within the patterns the extension asks for, over both schemes when it asks for both. When an extension's access changes, each loaded context withdraws what the old access granted and the new one does not (status `Unknown`), then is granted the new access again. A context that loses every host is unloaded around that and loaded again: WebKit files the scripts of a context that reaches every host under `*://*/*` and keeps running them on every new page until it loads again. For an extension on allowed sites that wants the active tab's host (`hasInjectedContentForURL`, or a requested pattern matching it), `extension_actions` reports the host and whether it is allowed, and the menu offers Allow or Remove under its row, then reloads the tab. In a private workspace allowing goes to the workspace's own context unsaved (`set_session_site`); stopping a saved host changes the settings wherever it is done. Settings switches the access and lists the allowed hosts.
- **Pinned buttons and badges**: `InstalledExtension.pinned` (toggled from the menu, through `install::change`) puts an extension's own button, with its badge, beside the puzzle button. The address bar keeps `extension_actions` for the workspace and active tab in a query while anything is pinned, refetched when the active tab changes, on `wis-extensions-changed`, and on `wis-extension-actions-changed`, which the controller delegate's `didUpdateAction` emits for its workspace. Icons are encoded once per image (`actions::icon_url`, holding the image so its address cannot be reused), since badges re-list the actions often. `extension_dismiss_popup` names the extension whose popup a click found open or just closed: the puzzle button stops on any, a pinned button only on its own, so clicking another extension's button while a popup is open opens that one.
