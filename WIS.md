# WIS.md

Wis loads `WIS.md` from the workspace root as agent memory (similar to AGENTS.md / CLAUDE.md). This file is also the project's living architecture doc.

**Read it before making changes, and update it whenever you change architecture, add a crate/module, or ship a user-facing feature.** Keeping this file accurate is part of "done" for any change.

## Project

**Wis**: open-source, fast, safe and lightweight browser that draws inspiration from browsers like Zen and Firefox. macOS-first; Windows is a growing tier-1 port (vault via DPAPI + Windows Hello, Mica glass, and a widening set of webview features reached through the `win_webview2` WebView2 helper, see Cross-platform conventions) with Linux to follow the same shape; a few native pieces (session/history restore, session-cookie persistence, per-tab memory) remain macOS-only today.

- Bundle id: `app.myk.wis`
- Package manager: **pnpm**
- Run/build: use the `Makefile` (`make dev`, `make build`, `make check`, `make test`, `make lint`, `make fmt`). `make dev` runs `pnpm tauri dev`; the built-in Tor client is a **default cargo feature**, so a plain `make dev` already includes it.
- Frontend check: `cd crates/shell && pnpm build` (= `tsc && vite build`; this is the typecheck gate, there is no separate test script yet).
- Rust checks: `make lint` (`cargo clippy --workspace --all-targets -- -D warnings`) and `make test` (`cargo test --workspace --all-targets`).

## Quality bar

Production-grade or it does not ship. Every change is judged against all of these, not just "it works":

- **Correctness**: edge cases, failure modes, concurrent access. No "works for now".
- **Performance**: ultra-lightweight is the product. For every change ask: how much RAM it costs, whether it adds IPC round-trips or redundant requests, whether it triggers extra re-renders or wasted work, whether it pulls a heavy dependency. Unused features consume zero resources (gate heavy deps behind cargo features, start subsystems lazily).
- **Security**: no critical security holes. Validate at every boundary (IPC, fs, network). Secrets are never logged. Page webviews (`tab-<uuid>`) are never granted Tauri capabilities.
- **UI/UX**: polished, professional, premium. Every state and detail considered.
- **Architecture**: new or changed logic lives in pure, dependency-light functions (functional core); tauri commands and React components stay thin (imperative shell). Keeps it testable without a later rewrite.

Verify before claiming done: `pnpm build` (frontend), `make lint`, `make test`. A change to a core subsystem (main browser, storage, network) needs a test that locks the invariant.

## Conventions

- **Comments**: default to none, the code should explain itself. If genuinely needed, 1-2 lines on *why*, never *what*. No AI-generic filler.
  - Avoid the use of "we" in comments, be explicit and direct: "this runs on startup" instead of "we run this on startup".
- **No em-dash** anywhere: code, comments, commits, docs.
- **No emojis** anywhere.
- **Imports**: always `@/...` on the frontend, never relative across modules.
- **pnpm only**, never npm/npx/yarn.
- **References to plans**: references to phases in the implementation plan/roadmap should be avoided in code/comments/docs.
- **Immutability**: every state transition returns a new value; never mutate in place. (`Tab` is `Clone + PartialEq` but not `Eq` because it carries an `f64` zoom.)

## Architecture

### Crate overview

Cargo workspace, five crates. Dependencies flow strictly downward: upper layers import lower ones, never the reverse.

```text
wis-browser-app  (crates/shell/src-tauri)  - Tauri shell, IPC commands, AppState, native macOS glue
       |
  wis-network    (crates/network)           - privacy decision engine, proxy, DoH, Tor
       |
  wis-storage    (crates/storage)           - Storage trait + SQLite implementation
       |                 \
   wis-core      (crates/core)   wis-secrets (crates/secrets) - vault crypto + keychain
   (pure data model, no I/O)
```

**`wis-core`**: dependency-light, pure data model. Defines `BrowserState` (root aggregate), `Workspace`, `Tab`, `UserSettings`/`UserSettingsPatch`, and typed IDs (`WorkspaceId`, `TabId`, `TabFolderId`, `WidgetId`). Modules: `state`, `workspace`, `tab`, `tab_folder` (`TabFolder` live-tab grouping), `settings`, `layout` (`LayoutMode`/`RailSide`/`ThemeMode`), `pane` (`PaneNode`/`SplitDir` binary split tree), `privacy` (`PrivacyMode`/`PerSitePolicy`), `proxy` (`UpstreamProxy`: `Socks5`/`Tor`), `search` (`SearchEngine`), `keybinding` (`KeyAction` enum + default/effective keymaps), `link_safety` (pure heuristic `assess_link` for Peek), `new_tab` (launchpad config: `NewTabTarget`, `ShortcutTile`, and boundary sanitizers `sanitize_homepage`/`sanitize_shortcuts`), `user_agent` (`UaProfile` + pure UA-string builders / `ua_for_host`), `download` (`DownloadStatus` transitions + `sanitize_filename`/`unique_filename`, the security boundary for server-suggested download names), `background` (`Background::Gradient/Image` + boundary validation for per-workspace backgrounds), `icon` (`parse_icon_ref` validating encoded `glyph:`/`glyph-fill:`/`emoji:` references), `theme` (`CustomTheme`/`ThemeTokens` + validation, versioned `.wistheme` envelope), `backup` (`BackupPayload`: optional per-category sections of an encrypted profile backup, with boundary validation and id re-mint so a merge-on-import never collides), `design` (`ChromeDesign`: chrome geometry/material knobs - corners, tab/folder shape, liquid-glass scopes + intensity, active-tab indicator, density, close-button, sidebar width; every variant defaults to today's look, `sanitized()` clamps the one numeric field), `widget`, `ids`, `error`. All mutation operations are pure `with_*` builders returning a new value.

**`wis-secrets`**: vault cryptography and master-key storage, isolated from the rest. Entries are sealed with ChaCha20-Poly1305 (AEAD, fresh random nonce per seal) under a 32-byte master key. The master key is generated with the OS CSPRNG and kept in the OS secure store, this-device-only: the **macOS login Keychain**, or on **Windows a DPAPI-sealed blob** in the per-user app data folder (beside `wis.db`; DPAPI only encrypts, unlike the Keychain it provides no storage, so the sealed blob is written to a file (user-scoped), so it is useless to another account or a stolen disk, the analogue of the Keychain ACL). The `keychain_*` function names are the cross-platform key-store surface (DPAPI-on-disk on Windows, not a literal keychain). The key is released into memory only after a biometric check (Touch ID / Windows Hello, enforced by the shell); the in-memory copy zeroizes on drop (`zeroize`). All key-store branches are pure of crypto and gated by `#[cfg]`. Plaintext exists only transiently and is never logged or persisted.

**`wis-storage`**: persistence layer. `Storage` trait is the only interface the rest of the app codes against; `SqliteStorage` is the sole production implementation (bundled SQLite via `rusqlite` + `rusqlite_migration`, WAL + `synchronous=NORMAL`). Persistence is **normalized tables, not a JSON blob**: `BrowserState` is saved/loaded across `workspaces`, `tabs`, `essentials`, `settings`, `meta` in one atomic transaction. Separate append-style stores live alongside it: `history` (per-workspace, deduped by url), `credentials` (vault ciphertext), `searches` (URL-bar search history), and `bookmarks` (+ `bookmark_folders`, per-workspace, foldered; `folder_id` NULL = unfiled; `pinned`/`pin_position` flag the quick-access row independently of the folder), `session_cookies` (per-workspace **encrypted** snapshot of in-memory session cookies, for stay-logged-in across restarts), and `downloads` (global completed-download history; in-flight/failed/cancelled downloads live only in shell memory). Migrations are append-only `M0001`..`M0014` (`migrations.rs`; `M0010` adds `pinned` + `pin_position` to `bookmarks`, `M0011` adds `session_cookies`, `M0012` adds `session_cookies.created_at` for the absolute session TTL, `M0013` adds a JSON `tab_folders` column on `workspaces` + `folder_id` on `tabs` for live-tab folders, `M0014` adds `downloads`, `M0015` adds a JSON `background` column on `workspaces`, `M0016` adds `workspaces.custom_accent`, `M0017` adds a JSON `workspaces.background_drafts` column). Live-tab folders persist like `pane_tree` (JSON column); a workspace's transient `selected_folder_id` is **session-only** and reset to `None` on load. Crash resilience: `backup_to()` writes a consistent standalone copy via `VACUUM INTO`, and the shell's resilient open refreshes that backup on a healthy launch and recovers from it (or starts fresh) if the primary DB is corrupt. Ephemeral (private) workspaces are skipped on save, so they never touch disk.

**`wis-network`**: privacy decision engine. Contains:

- `TrackerBlocker` (`blocker.rs`): wraps the `adblock` crate; parses EasyList/EasyPrivacy rules once. The compiled engine is memoized on disk (`engine-<hash>.bin` beside the filter-list cache, keyed by a hash of the input texts, stale versions pruned): a warm launch deserializes the engine instead of re-parsing the list, and the self-versioned DAT format falls back to a fresh parse on any mismatch (crate upgrade, corruption). Both the startup build and the runtime EasyPrivacy refresh go through the cache.
- `filter_lists/`: bundled fallback list plus background `fetch` of fresh EasyPrivacy (cache-staleness gated).
- `content_filter.rs`: compiles filter rules to a WKWebView `WKContentRuleList` spec for engine-level blocking. Attachment is **lookup-first**: the `WKContentRuleListStore` persists compiled lists by identifier (the identifier hashes the rule JSON, so a refreshed filter list misses naturally), so the expensive compile (a full parse of EasyPrivacy-size JSON) runs once per filter-list version instead of on every tab creation and launch; startup prunes stale `wis-cb-*` entries from older list versions.
- `HttpsUpgrader` (`upgrader.rs`): HTTPS-First enforcement.
- `DohResolver` / `StubResolver` (`resolver.rs`): DNS-over-HTTPS via `hickory-resolver`; stub is the no-endpoint fallback.
- `RequestPolicy` (`policy.rs`): combines a workspace's `PrivacyMode` with the blocker into an allow/block/redirect `Decision` per request.
- `proxy/`: loopback HTTP proxy (hyper) per workspace. Forwards plain HTTP, tunnels HTTPS `CONNECT`, applies HTTPS-First redirects, drops trackers. Policy is **hot-swappable via `tokio::sync::watch`** (read per request) so changes never rebind the port. Supports an optional `upstream` (`proxy/upstream.rs`, `connect.rs`): SOCKS5 or Tor. The direct path (`connect.rs`) DoH-resolves then dials **every** returned address in turn, each under a per-address connect timeout (and the lookup itself under a resolve timeout), so an unreachable address (e.g. an AAAA answer on a network with no IPv6 route) falls through to the next instead of stalling the `CONNECT` tunnel forever.
- `tor.rs`: built-in Tor via `arti-client`, exposed as a loopback SOCKS5 endpoint (`TorProxy`). Behind the `tor` cargo feature (**on by default**; build `--no-default-features` to omit).

**`wis-browser-app`** (`shell/src-tauri`): Tauri app wiring. `AppState` holds: `browser: Mutex<BrowserState>`, `window_workspaces: Mutex<HashMap<WindowLabel, WorkspaceId>>` (the **active workspace is per-window**, not global: a window is a view over one workspace; seeded with `main` at startup, `get_browser_state` returns the calling window's entry, `set_active_workspace` keeps it in sync, and `BrowserState.active_workspace_id` stays the persisted primary the `main` window restores to), `storage: Arc<dyn Storage>`, `tracker_blocker: RwLock<Arc<TrackerBlocker>>`, `resolver: Arc<dyn Resolver>`, `content_rules` (per-`PrivacyMode` compiled rule cache), `filter_cache_dir`, `proxies: Mutex<HashMap<WorkspaceId, ProxyServer>>` (lazy, one per workspace), `vault_key: Mutex<Option<MasterKey>>`, `pending_capture` (save-password prompt), `closed_tabs` (reopen ring), `last_screenshot` (PNG of the most recent capture, held so the success toast's Save button can write it to disk), and `tor_proxy` (lazy, `tor` feature). Native modules: `commands` (IPC), `state`, `menu` (accelerators -> `wis-keyaction` events), `overlay` (floating webviews), `find`, `cookies`, `favicons`, `biometrics` (Touch ID via LocalAuthentication, or Windows Hello via `UserConsentVerifier`), `vault`, `capture` (save-password channel: a `WKScriptMessageHandler` on macOS, the `win_dispatch` receiver on Windows; host read from the engine, never the page), `suggest`, `content_filter`, `pane_focus` (click-to-focus: an `NSEvent` mouse monitor on macOS, a per-controller `add_GotFocus` handler on Windows), `peek` (Opt+click link preview), `reader` (in-page article transform shared by full-page reader mode and Peek), `screenshot` (clipboard-default PNG capture, visible / region, with a top-right success toast that offers Save), `backup` (encrypted profile export/import: passphrase-encrypted `.wisbackup` file), `link_open` (Cmd/middle-click open-in-tab), `navguard` (navigation safety interstitial), `video_popout` (floating always-on-top video mini player in its own window), `audio` (per-tab audibility + engine-level page mute, cross-platform), `win_webview2` (Windows: shared access to the WebView2 COM handles behind a Tauri webview, the cross-platform-feature port layer; also the container-HWND helpers: `SetWindowRgn` corner rounding registered per label and re-cut on every bounds change, `promote_to_front` z-order repair, `move_focus`), `win_focus` (Windows: subclasses each browser window's frame HWND and forwards a frame-level `WM_SETFOCUS` into the active tab webview or the chrome, since wry skips its own focus-forwarding subclass for child webviews and every Wis webview is one), `win_dispatch` (Windows: the single `add_WebMessageReceived` receiver that multiplexes the per-feature `wisOpenInTab`/`wisPeek`/`wisNavGuard`/... channels WKWebView gives each its own named handler for; a document-start shim recreates `window.webkit.messageHandlers` so the page scripts post unchanged), `bookmarks` (per-workspace foldered bookmark CRUD), `external` (hand a URL to the OS default browser), `permissions` (per-site camera/microphone consent prompt), `error_compat`.

### IPC command pattern

Every mutating command goes through `mutate`:

1. Acquire the async mutex on `BrowserState`.
2. Snapshot previous state for rollback.
3. Compute next state via a pure `with_*` transition from `wis-core` (no I/O inside the closure).
4. Persist next state via `Storage::save_state`.
5. On persist failure: revert in-memory state and surface `WisError::PersistenceFailed`.

After a successful mutation the command emits `browser-state-changed`; the frontend re-fetches `BrowserState` via React-Query (the query cache is the single source of truth on the JS side). Read-only commands hold the mutex only long enough to clone the relevant slice.

### Webview compositing and overlays (important)

Native tab webviews (`tab-<uuid>`) composite **above** the chrome webview, so HTML chrome cannot draw on top of a page. Any floating UI that must sit over a page (find bar, command palette, URL-bar suggestions, clear-data dialog, vault menu, pane-split menu, Peek) is therefore a separate **overlay webview**, positioned natively and routed in `overlay/OverlayRoot.tsx` to a surface in `overlay/surfaces/`. Overlays are **per-window**: the label is `overlay-<window>-<name>` so each OS window has its own find bar/palette/etc. (`overlay.rs::ensure_overlay` builds the label from the calling window; the overlay commands `set_overlay_bounds`/`size_overlay`/`hide_overlay` resolve it the same way). `main.tsx` picks the surface from the **URL query** (`index.html?surface=<name>`), not the label, so the window prefix doesn't affect routing; the chrome webview loads `index.html` with no query and renders the full App. A surface focuses itself with `focus_self` (the calling webview becomes first responder, no label), so it works on any window.

**Multi-window** (`windows.rs`): the browser is **one OS window per workspace** (in-window multitasking is the pane split). `new_window(workspace_id)` builds a secondary `WebviewWindow` labelled `win-<uuid>` that loads the same chrome bundle as `main`, binding it in `AppState::window_workspaces` *before* the build so the chrome's first `get_browser_state` resolves to that workspace; the window mirrors `main`'s glass treatment via `windows::chrome_window_effects()` (the HUD vibrancy on macOS, **Mica** on Windows 11, none elsewhere), plus the Overlay title bar and disabled shadow. **New Private Window** opens such a window over a fresh ephemeral workspace (no picker); **New Window** opens the **free-workspace picker** (`WindowPickerSurface`, a content-area overlay managed by `useWindowPickerOverlay`, modelled on the command palette): the `new_window` keyaction (focus-scoped) dispatches a DOM event that shows it, listing `free_workspaces` (persistent workspaces no window currently shows; the calling window's own is occupied too) plus a *New empty workspace* row. Selecting a workspace calls `new_window(workspace_id)`; *New empty workspace* creates a persistent workspace + first tab, then opens a window for it. A secondary window's `window_workspaces` bind is cleared when the window is `Destroyed` (a per-window `on_window_event` handler), so closing a window frees its workspace back into the picker. The one-workspace-per-window invariant is enforced on every switch/open: `set_active_workspace` and `new_window` resolve `window_for_workspace(id)` first and, if another window already shows it, **focus that window** (`focus_window`: deminiaturize + `set_focus`) instead of duplicating the workspace (two windows over one workspace would conflict its `tab-*` webviews). On collision `set_active_workspace` is a no-op for the caller, whose `invalidateQueries` refetch self-heals its UI back to its own workspace; `new_window` returns the existing owner's label. **Session restore**: the windowed set is persisted **continuously**; every `set_window_workspace` / `clear_window_workspace` writes the current snapshot via `Storage::save_windowed_workspaces` (a `meta` key that, unlike the document tables, survives `save_state`'s `clear_all`). Continuous rather than at-exit so it survives a non-graceful exit (a `make dev` stop never fires `RunEvent::ExitRequested`); startup seeds `window_workspaces` directly (not through the setter), so the saved set is intact when, on launch, the `main` window calls `restore_session_windows` once (process-guarded by `AppState::session_restored`), which `spawn_window`s each saved workspace not already shown. Deleted or ephemeral (private) workspaces resolve to nothing and are skipped, so private windows never restore. Each window's **geometry** (logical position/size) is persisted **per workspace**, not per label (`win-<uuid>` labels are fresh each run, so Tauri's window-state plugin can't match them): `record_window_geometry` snapshots it on every `Moved`/`Resized` into `AppState::window_geometry` and writes the map under a `window_geometry` meta key, debounced by `geometry_gen` so a drag-burst coalesces to one write (and survives a `make dev` stop). `spawn_window` applies the saved geometry at *build time* (no reposition jump); the `main` window is declared `visible: false` in `tauri.conf.json` and positioned-then-shown in `setup`, so it too restores without a jump. **Move to New Window** (tab context menu) tears a tab out into its own window: since a window *is* a workspace, `move_tab_to_new_window` creates a fresh workspace (private when the source workspace is, so private content never persists), recreates the tab in it (`with_new_loose_tab` + `with_tab_closed`, atomically), then `spawn_window`s it. The torn-out tab keeps its history/scroll despite the webview being rebuilt in the new window: the command captures the source webview's `interactionState` and stashes it under the new tab id in `pending_restore_states`, which `create_tab_webview` replays. The same menu's **Move to workspace** section (`move_tab_to_workspace`) relocates a tab into an existing persistent workspace by the same recreate-and-carry-session path (a fresh tab id, so no cross-window `tab-*` clash; refuses to move a private tab into a persistent workspace). Both that menu and the sidebar workspace popover refetch `BROWSER_STATE_KEY` on each open, since the global query is `staleTime: Infinity` and window open/close changes don't broadcast, so their lists would otherwise lag. The chrome bundle is window-agnostic (de-`main`-ed the native layer): it reads its own label from `getCurrentWindow()` and routes tab/overlay/peek/widget creation to that window, so a secondary window behaves exactly like `main` over its own workspace. The window is built (and its shadow disabled) on the **main thread** via `run_on_main_thread`, and so must **every AppKit call reached from a command**, because commands run on tokio workers and off-main AppKit crashes non-deterministically. This bites anything that touches Cocoa directly rather than through a Tauri/`with_webview` handle (which already hops to the event loop): e.g. `set_dock_icon`'s `setApplicationIconImage:` drives `-[NSDockTile display]` -> CoreGraphics, so it must be wrapped in `run_on_main_thread` (a new private window calls it with `"closed"` on mount, which otherwise segfaults in CoreGraphics on the worker); native open/save panels (`runModal`) are already either dispatched there or invoked from wry's main-thread callbacks. The Dock icon is **process-global** but the model is one workspace per window, so `useDockIcon` only drives it while its window holds focus: the focused window claims the icon for its own privacy state (closed-eye owl when private), re-claiming it on every `onFocusChanged` focus-gain and when its workspace's privacy flips (the per-window titlebar icon is separate, via `useWindowIcon`). **App-wide broadcast events must be focus-scoped**: `wis-keyaction` (menu/accelerators) and `wis-peek-open` (Opt+click) are emitted with `app.emit`, which reaches every window, and a Tauri listener on the default `Any` target always matches (so a backend `emit_filter` cannot exclude it). Because it is one workspace per window, an ungated broadcast would e.g. open a tab in every window at once, so each listener gates on `lib/windowFocus.ts::isWindowFocused()` (tracked via `onFocusChanged`) and only the focused window acts. The same app-wide gotcha applies to **webview enumeration**: `Webview.getAll()` returns every window's webviews, so `useTabWebviews`'s mount cleanup (which closes leftover `tab-*` webviews) filters by `wv.window.label` to its own window, otherwise an opening secondary window would close a sibling window's live tab webviews, crashing it or leaving it blank. Likewise the native **subview re-stacking** helpers (`promote_panels_to_front` / `promote_overlays_to_front`) filter by the *per-window* panel/overlay label prefix: subview order is per `NSWindow`, so a new window restacking another window's still-loading panel views is both pointless and crash-prone (the trigger was opening widgets and immediately spawning a window). The **`wis-asset` wallpaper protocol** answers chrome surfaces only, `main`, secondary windows (`win-*`), and any window's `overlay-*` webviews, so a secondary window renders its workspace's saved wallpaper while tab/widget pages still get 403.

The capability boundary is **local vs remote content**, not just the window: the `default` capability has no `remote` block, so it applies only to local app webviews (the chrome + `overlay-*` surfaces, which load the bundled `index.html`) on the windows its `windows` glob matches (`["main", "win-*"]`, so secondary windows are covered). Tab pages and the Peek preview (`peek-page-<window>`) load remote `http(s)` URLs and match no command-granting capability, so they can never call a command. (The one exception is `tab-devtools.json`, which grants only the devtools-toggle to `tab-*` remote webviews.) Tab webviews route engine new-window requests by intent (`on_new_window`): a scripted popup that **declares geometry** (`window.open` with width/height/left/top, the OAuth-consent shape, e.g. "Continue with Google") or targets `about:blank` (the opener scripts into it) is **Allowed** as a native wry window using the opener's WKWebView configuration, sharing the workspace session + proxy and keeping the `window.opener` link OAuth needs (postMessage / window.close); a plain navigation (`target=_blank` links, featureless `window.open`) to the **opener's own site** (`popup_chrome::same_site`, an eTLD+1 approximation with a small ccSLD table, so `mail.google.com` and `accounts.google.com` are one site, e.g. Gmail's account switcher) is Denied and **navigated in the current tab**, while a **cross-site** one is Denied and re-emitted as `wis-open-in-tab-fg`, which the focused window opens as a normal foreground tab (`popup_chrome::wants_popup` is the discriminator; geometry presence is the only popup signal wry surfaces; widget panels share the routing minus the in-place branch, since navigating a widget app away is never right). The allowed popup is a bare wry webview with no Tauri capability, so the remote-content boundary holds. Popups **honor the page's `window.close()`** (an OAuth flow finishing, a compose window after send): wry gives the popup webview no `UIDelegate`, so WebKit's `webViewDidClose:` would be dropped; `popup_chrome`'s decoration poll therefore assigns an app-side delegate (`WisPopupUiDelegate`), which closes a window only when the webview *is* the window's content view (the engine-popup shape), so a browser window can never be closed by page script. That same delegate also implements `runOpenPanelWithParameters:`, so a file `<input>` inside a popup (e.g. **browse-from-computer in a popped-out compose window**) opens a native `NSOpenPanel`; without it WebKit silently no-ops the picker, because (unlike main tabs, which receive wry's own open-panel delegate) the engine popup has no delegate answering that selector. This shim is macOS-only: on Windows (WebView2) and Linux (WebKitGTK) the runtime renders the file dialog itself with no host delegate, so the popup file picker already works there. Because the popup window is built inside wry (no shell handle, and the vendor stays unpatched), its **read-only address bar** is added app-side (`popup_chrome.rs`, macOS): when `on_new_window` fires it hands `popup_chrome` the target URL, which decorates the just-created window on the next main-loop tick (so the titlebar accessory appears with the window, no content jump) and keeps a refresh poll alive for later redirects. The accessory is a read-only URL field plus a scheme glyph (lock for https, warning for http); it is **seeded with the open target URL** because the popup's `WKWebView` reports `about:blank` until it navigates (and `window.open('')` OAuth targets never carry one), then tracks the live URL as the popup redirects. The poll self-stops once every popup closes, so it costs nothing when none are open. Detection is precise: child webviews (tabs, widget panels, overlays, Peek) are subviews of the main window, and every Tauri-managed window (main, video popout) is excluded via `ns_window()`, leaving only engine `window.open` popups (including those opened from widget panels). **Cmd/middle-click a link** must instead open a new *tab*, not a popup: a builder-level page script (`link_open::page_script`) intercepts `Cmd`/`Ctrl`+click and middle-click on `<a href>` (Opt+click stays peek's), `preventDefault`s WebKit's open-in-new-window, and posts the href to the `wisOpenInTab` handler, which emits `wis-open-in-tab`. The focused window opens it as a **background** tab in its workspace (`create_background_tab` -> `with_new_background_tab`, which appends without stealing focus). Real `window.open`/`target=_blank` (which the script never touches) go through the `on_new_window` routing above (geometry popups stay native, plain navigations become foreground tabs). **Chrome surfaces mirror the same middle-click contract** (cross-platform, plain `onAuxClick` -> `create_background_tab`): launchpad quick-access tiles and history rows open in a background tab and stay on the page, and bookmarks-menu rows open in a background tab **keeping the menu up** so several can be opened in a row (the tab strips' middle-click still means close). Every chrome middle-click target (including the tab strips) also `preventDefault`s the **middle-button mousedown**: Chromium engages its pan/autoscroll at mousedown, which `auxclick`-time preventDefault is too late to stop, the same guard `link_open`'s page script uses (inert on WebKit). Palette and URL-bar suggestion rows are deliberately excluded (transient keyboard-driven surfaces).

### Frontend (React / TypeScript)

Lives in `crates/shell/src/`. Imports use `@/...` aliases; relative cross-module imports are forbidden.

**Components** (`src/components/`): `Window` (root layout host), `TopBar`/`NavRow`/`TopTabsRail` (chrome), `UrlBar` (address input + HTTPS security indicator + vault key button), `Sidebar` (ends in a docked footer cluster: downloads, bookmarks, VPN, history, settings)/`WorkspacePill`, `TabList`/`HorizontalTabs`/`TabFolderHeader`/`PinnedTabs`/`TabFavicon`, `TabWebViewHost`/`SplitPaneHost` (mount native webviews to measured rects, one per visible pane leaf), `Content`, `SettingsPage` (with `AppearanceSection`, `DesignSection`, `PasswordsSection`, `SiteDataSection`, `KeybindingInput`), `HistoryPage`, `NewTabPage`, `VpnToggle` (Tor on/off), `ConfirmDialog`, `Brand`/`WisMark`, `controls`. The **Design** settings page (`DesignSection` + `ThemesSection`) exposes `ChromeDesign`: `useThemeApply` mirrors each field onto `<body>` as a `data-*` attribute or CSS var (`data-corners`/`data-glass` drive `--radius-scale`/`--glass-scale` multipliers in `tokens.css`; `glass-chrome`/`glass-menus`/`glass-tabs` scope classes gate the master `glass-on`; `--sb-w` is set inline) and the variant blocks in `window.css` do the rest. Themes export/share as `.wistheme` files or portable `wis-theme:<base64>` clipboard codes (`encode_theme_code`/`decode_theme_code`, same validate-and-re-mint path).

**Lib** (`src/lib/`): `cx`, `icons`, `url`, `keybindings`, `palette`, `urlbarSuggest`, `vaultMenu`.

**Bindings** (`src/bindings/`): typed wrappers for every IPC command (`commands.ts`) and shared types mirroring `wis-core` (`types.ts`). Wrappers accept camelCase and translate to serde's wire format at the boundary.

### Window styling

- Chrome surfaces use background tiers for contrast: `--content-bg` (inside the periwinkle border: settings/new-tab/webview, transparent in glass so it shows the OS vibrancy), and darker `--chrome-bar` / `--chrome-bar-glass` for the chrome frame (side bar, top bar, rail) and the margin **around** the content. The frame around the content is painted with a large `box-shadow` spread on `.kb-content` (clipped by `.kb-main { overflow: hidden }`) so the margins match the bars without darkening the content. Bars that float over the main area (collapsible sidebar, top-tabs rail) are left transparent so they reveal that same frame shadow rather than stacking a second dark layer.
- Split panes reuse this idea as a "cut-out": each pane `.pane-surface` is a transparent rounded window (the page shows the OS vibrancy straight through it) whose **outset** `box-shadow` draws the periwinkle pane ring (full accent on the focused leaf) and then floods everything outside the window (including the rounded-corner slivers) with the same frame tone, clipped to the pane's slot (`.pane-slot { overflow: hidden }`). An outset shadow never paints inside its own box, so the page stays fully transparent; the surface radius matches the native webview corner radius so opaque webview panes and transparent chrome panes fill identically and show no light gaps. Off macOS the pane ring is **square** (`body:not([data-platform='macos'])`; `main.tsx` stamps `data-platform` at boot): native webview corner rounding is macOS-only (`set_webview_corner_radius` no-ops elsewhere), so a rounded ring would visually disconnect at every corner of the square WebView2 surface. `.kb-content.is-split` also zeroes its **border width** (not just colour) so no thin ring of bare vibrancy shows between the pane group and the chrome-bar frame.
- Scrollbars (chrome webview only) use a single global `::-webkit-scrollbar-thumb` whose colour is the `--scrollbar-thumb` token, **inverted vs the theme** (light thumb in dark mode, dark thumb in light) so it stays visible on any surface; large chrome pages just widen it.
- macOS: `titleBarStyle: Overlay` + `hiddenTitle: true` (native traffic lights via overlay); chrome webview shadow disabled to avoid a glass flash on navigation.
- Linux: `decorations: false` + `transparent: true`; re-asserted post-realize for GNOME/Mutter CSD.
- Windows: the chrome glass is **Mica** (Windows 11; `windows::chrome_window_effects()` returns `WindowEffect::Mica`, applied to secondary windows at build time and to the conf-built `main` window via a `set_effects` call before reveal, since `tauri.conf.json`'s `hudWindow` is macOS-only and a no-op there). Windows 10 silently gets no glass (Tauri swallows `apply_mica`'s error). Native window controls / custom decorations are not wired yet (the window keeps the default frame on Windows).

### Cross-platform conventions

- HOME / cache dirs: use the `dirs` crate, never raw `$HOME` / `%USERPROFILE%`.
- **Page -> chrome message channels**: WKWebView gives each feature its own named `WKScriptMessageHandler` (`window.webkit.messageHandlers.<name>`); WebView2 has only one pipe (`window.chrome.webview.postMessage` -> a single `add_WebMessageReceived`). The page scripts stay identical: on Windows `win_dispatch::SHIM_SCRIPT` (a document-start init script) recreates `window.webkit.messageHandlers` so each named `postMessage` forwards a `{ handler, body }` envelope, and `win_dispatch::install` registers the one receiver that parses it and calls the same per-feature logic the macOS handler would (the per-feature `install` fns are macOS no-ops there). Wired: `wisOpenInTab`, `wisNavGuard`, `wisPeek`, `wisMediaPermission` (its `getUserMedia` gate `GATE_JS` rides the tab builder as a Windows init script, and a remembered decision resolves via `webview.eval`), and `wisCapture` (save-password: its `CAPTURE_JS` likewise rides the builder, the host is read from the webview's own URL not the page, and the dispatcher gates the channel off for ephemeral tabs so private logins are never captured), and `wisCosmetic`/`wisZap` (cosmetic element-hiding + the element zapper). The cosmetic/zap arms are gated to non-Permissive workspaces and to the **top frame**: WebView2 runs every init script in subframes too (wry can't restrict to the main frame) and the single dispatcher can only eval a reply into the main frame, so `is_top_frame` compares the message's `args.Source` to the webview's top-level URI and drops iframe-originated cosmetic/zap (a zapped host is read from the webview URL, never the page). Still logging "not yet wired": only `wisPopout` (deferred to the runner).
- **Keyboard accelerators** are authored once in macOS form (`Cmd+T`) and localized to the host. The native menu is the real keystroke handler, so the source of truth is Rust: `keybinding::default_keymap()` delegates to `default_keymap_for(cfg!(target_os = "macos"))`, which swaps the `Cmd` token for `Ctrl` on Windows/Linux (muda would bind a literal `Cmd` to the Windows/Super key, so this is correctness, not cosmetics; `Alt`/`Shift`/keys are identical). The frontend keymap is **display-only** and mirrors this: `lib/platform.ts::isMacOS()` (synchronous `navigator.userAgent` sniff, since the chrome webview runs on the host engine) drives `lib/keybindings.ts::localizeAccelerator` (the same `Cmd`->`Ctrl` swap, applied to the `DEFAULT_KEYMAP` mirror) and `prettyAccelerator` (glyphs `⇧⌘G` on macOS, textual `Ctrl+Shift+G` elsewhere). Override capture is inherently portable: `keyboardEventToAccelerator` records the physical modifier (`ctrlKey`->`Ctrl`), so a Windows rebind stores `Ctrl+...` directly. On Windows/Linux the menu is installed but its **window bar is hidden** (`apply_menu` calls `app.hide_menu` after every `set_menu`, and `spawn_window` hides each new secondary window's bar): Wis drives every command from chrome UI, so the bar is redundant clutter; `muda`'s hide only drops the bar widget, leaving the Linux GTK accel-group attached. **Dispatch is per-platform**: macOS uses the global-menu accelerators and Linux the GTK accel-group (both native), but on Windows native accelerators **never fire** (a focused WebView2 handles input out-of-process, so keystrokes bypass Tauri's `TranslateAcceleratorW` message hook and wry does not forward `AcceleratorKeyPressed`), so shortcuts are dispatched in JS, per focus location: the chrome webview and every **overlay** webview mount the same keydown hook (`useKeybindCapture`; `Window.tsx` with `takeFocusOnMount`, `OverlayRoot` without, so the find bar/palette are not shortcut dead zones), and every tab webview gets an injected forwarder (`keybind.rs`, keymap baked in at creation, rebinds pushed live via `keybind::apply_to_all_tabs` eval, which reaches top-level documents only, so an iframe keeps the old keymap until it next navigates). The tab forwarder is **two-tier**, mirroring both macOS and mainstream-browser priority: a chrome-owned `RESERVED_ACTIONS` set (tab/window lifecycle + address-bar focus) is stolen at capture phase before the page sees the keystroke, while everything else is **page-first**, dispatched from a bubble-phase window listener only when no page handler `preventDefault`ed (so Ctrl+S in a web editor saves the document instead of toggling the sidebar, matching WKWebView offering key equivalents to the page first on macOS). Matched ids post over the `wisKeybind` dispatcher channel, whose arm is **provenance-gated**: the posting webview must be a workspace's current active tab (a fabricated post from a background tab is dropped) and the re-emitted `wis-keyaction` event is stamped with the source tab, which `useKeyActions` requires to belong to its own window's workspace, so web content can never drive another window's chrome; residually, the page the user is actively viewing can still fabricate actions against itself (nuisance-tier, documented in `keybind.rs`). Menu/chrome dispatches carry no source tab and pass. Accelerator matching is normalized identically on both sides (`normalizeAccelerator` in `lib/keybindings.ts` and its mirror inside `KEYBIND_JS`: Option/Alt unified, modifiers ordered, shifted symbols folded so `Ctrl+Shift+]` matches a `}` keystroke), and `palette.ts::DEFAULT_KEYMAP_MAC` must stay in lockstep with `keybinding.rs::default_keymap_for` (both now drive live key handling, not just display; a drift means the same keystroke does different things in chrome vs page focus). **Startup focus** is the other Windows half: nothing used to give any webview keyboard focus at boot, and tao's `is_focused()` reads the top-level HWND flag (false whenever a WebView2 child holds focus), which poisoned the `isWindowFocused()` gate that all `wis-keyaction` listeners share, so keybinds were dead until a click. Fixes: `windowFocus.ts` ORs `document.hasFocus()` into the boot correction and treats DOM focus/pointerdown as focus evidence; `focus_self` gained a Windows implementation (controller `MoveFocus(PROGRAMMATIC)` via `win_webview2::with_controller`, also un-breaking every overlay surface's `focusSelf`); the chrome calls `focusSelf` once on mount and `lib.rs` follows `main.show()` with `set_focus()` on Windows. The root of the whole class: tauri's multiwebview mode makes even the chrome a wry *child* webview, and wry only installs its frame `WM_SETFOCUS` -> `MoveFocus` subclass for non-child webviews, so any focus landing on the bare frame HWND (boot activation, alt-tab back, a focused webview closing) stranded keystrokes on a window nothing listens to - and the one-shot mount `focusSelf` raced the first activation and could lose. `win_focus::install` (called for `main` in setup and for every `spawn_window`) restores the missing subclass: on frame `WM_SETFOCUS` it forwards focus to the window's workspace's active tab webview, else the chrome webview, skipping if a click already routed focus into a webview by the time the async lookup lands (`GetFocus` still the frame check). The chrome side holds the complementary invariant: whenever a chrome page (settings, launchpad) is the active surface, no tab webview claims focus and the previously focused (now hidden) tab webview would keep swallowing keystrokes, so `TabWebViewHost` pulls focus into the chrome (`focusSelf` retry loop gated on `document.hasFocus()`), and `close_peek` / the find-bar close hand focus back (`win_focus::restore_webview_focus` / `focus_webview`, which now has a Windows arm). macOS is untouched (global menu bar; `hide_menu` is a documented no-op there).
- **WebView2 environments (Windows)**: WebView2 runs one browser process per user-data folder, with the environment's browser arguments baked in at launch. Any webview builder that sets `proxy_url` (wry appends `--proxy-server` to those arguments) **must also set `data_directory`** on Windows, or it lands in the shared default folder whose already-running proxy-less browser process (the chrome webview's) makes environment creation fail with `ERROR_INVALID_STATE`. Wired: tab webviews and widget panels (per-workspace `workspace_webview_data_dir`), ephemeral-workspace tabs and Peek (per-workspace `ephemeral_webview_data_dir` / the workspace dir; InPrivate keeps data out of it, and setup sweeps `webviews-ephemeral` leftovers). The vendored wry additionally destroys the container HWND when any creation step fails (see `vendor/wry/WIS-PATCH.md`): the leak was a `WS_VISIBLE`, nothing-painting, fully hit-testable child window that silently swallowed mouse input over its rect (a failed Peek left the page center click- and wheel-dead).
- **Native webview stacking + rounding (Windows)**: HWND z-order is creation order and wry repositions with `SWP_NOZORDER`, so `promote_overlays_to_front` / `promote_panels_to_front` now have Windows arms (`win_webview2::promote_to_front`, `SetWindowPos(HWND_TOP)` on the container HWND) keeping tabs < widget panels < overlays just like the macOS `addSubview:` re-adds. Corner rounding is the macOS CALayer pair's analogue via `SetWindowRgn` + `CreateRoundRectRgn` on the container HWND (clips the scrollbar too); a GDI region is fixed-size, so the radius registers per label (the map is pruned against live webviews on each `set_corner_radius`, since tab webviews close frontend-side) and `set_tab_webview_bounds` / `set_peek_bounds` re-cut it on every resize. The split-pane CSS squaring override is now Linux-only (`body[data-platform='linux']`), since Windows panes round natively.
- **Native webviews eating input (Windows)**: a WebView2 child HWND hit-tests regardless of transparency and can keep capturing mouse input while hidden, unlike an empty transparent WKWebView that AppKit hit-tests through, so a stale or hidden webview over the content area silently kills clicks/scroll there (observed: settings toggles dead, the page below a peek wheel-frozen). Two guards: hidden tab webviews are parked offscreen on hide (`PARK_HIDDEN_OFFSCREEN` in `useTabWebviews`, Windows only) so a dropped/slow hide can never occlude; and the address-bar suggestions overlay no longer lingers, `useUrlbarSuggest.close` supersedes any in-flight `refresh` (bumps the request id) whose late `showUnderBar` would otherwise re-show the just-closed transparent overlay over the content column. The failed-creation container leak that caused the peek symptom is fixed in vendored wry (see `vendor/wry/WIS-PATCH.md`).
- **Native UX ports**: several macOS-AppKit features have Windows equivalents wired in the same per-feature module: clipboard copy (`clipboard.rs`, `NSPasteboard` / `arboard`, text-only so its image-data default is off), native save+open file dialogs (`panels.rs`, `NSSave/OpenPanel` on macOS, `rfd` on **both Windows and Linux** now, all shown on the main thread via `dispatch`; the non-macOS dialogs are not yet window-owned, a follow-up), split-pane click-to-focus (`pane_focus.rs`, an app-wide `NSEvent` mouse monitor / a per-controller `add_GotFocus` handler emitting `wis-pane-focus`, gated on a live `GetKeyState(VK_LBUTTON)` press so window-refocus and programmatic focus don't fire it, matching the macOS mouse-down semantics), and find-in-page (`find.rs`, WebKit's find SPI / a JS `CSS.highlights` engine that reports over the `wisFindResult` dispatcher channel; top-document only, and case-insensitivity is ASCII-only to keep match offsets length-stable). Open-in-default-browser is already cross-platform (`external.rs`, OS shell).
- **Deferred to a Windows runner** (no compile-only path; each needs runtime validation): session-cookie restore (Tauri's cookie API needs a live webview, but restore must precede the first load, which the builder creates-and-navigates atomically), uBO `+js` scriptlet swap (`AddScriptToExecuteOnDocumentCreated` would have to register inside the navigation event at document-start timing; re-entrant message-pump risk), video-popout reparenting, full session/history restore (no `interactionState` equivalent), window/region **composite** screenshot (visible-tab capture is done on Windows), and Linux viewport capture (WebKitGTK `WebView::snapshot`). Per-tab task-manager memory stays an honest empty on Windows (WebView2 shares one process group with no per-tab renderer pid).

## Features

- **Workspaces**: color-accented profiles; each gets its own WebView data store, proxy, and privacy mode. Store isolation is the WKWebView `data_store_identifier` on macOS and a per-workspace WebView2 user-data folder on Windows (`commands::workspace_webview_data_dir`, applied to tab and widget-panel webviews); WebView2 ignores `data_store_identifier`, so without the folder split every persistent Windows workspace would collapse into one profile and share a cookie jar.
- **Private browsing**: private = an *ephemeral* workspace with a non-persistent data store; excluded from save, wiped on close. "Always launch private" setting; private window icon.
- **Split panes**: per-workspace binary `PaneNode` tree (tmux-style), resizable dividers, focused-leaf highlight; each leaf is its own native webview. Native click-to-focus routes keybinds to the focused leaf.
- **Pinned tabs**: a tab can be pinned (`Workspace.pinned_tab_ids` + `Tab.pinned`, kept in sync by `pin_tab`). Pinned tabs are pulled out of the normal tab list/strip and shown as a docked quick-access set, present in every layout. In the **collapsible sidebar** (`PinnedTabs`) they are a favicon grid (rows of three) under the workspace pill: clicking a cell activates the tab, the title is the tooltip, the active one is ringed; collapsed, the grid becomes a single workspace-pill-sized **pin glyph** (a generic pin glyph rather than many favicons, matching the workspace pill) that the sidebar reveals by expanding (auto on hover; the glyph also expands it). In the **top-tabs** layout they are favicon-only circles docked at the start of the strip (ordered by `RailSide` so they always sit nearest the rail), draggable to reorder; the active circle shrinks so bubble + ring keep the normal footprint while the favicon stays put. Pin/unpin lives on the tab context menu (the right-click directional split pill, `overlay-tabmenu`): a divider then a pin toggle that calls `pin_tab`. Pinned tabs never sleep and never sit inside a folder. Reordering the remaining tabs reorders only the non-pinned subset and merges back so pinned tabs keep their slots in `tab_order` (`reorderedWithPinned`).
- **Tab folders**: open tabs can be grouped into per-workspace, named, recolorable folders (`wis_core::tab_folder::TabFolder` { id, name, accent, collapsed, position }; `Workspace.tab_folders` + `Tab.folder_id`, mutually exclusive with pinned). Distinct from bookmarks (those save URLs; folders organise *live* tabs). In the **sidebar** (`TabList` + `TabFolderHeader`) they render as an IDE-style tree: a colored name pill + chevron + member rows beside an inset accent rail; in the **top-tabs** strip (`HorizontalTabs`) they render as **islands**: a colored circle when collapsed, an expanded glass pill (colored name chip + its tabs) when open. Both support create, inline rename, recolor (accent swatches), collapse, delete (members stay open, re-parented loose), and pointer-drag reorder; a tab can be dragged onto a folder to file it, dragged out to empty strip/loose space to unfile, reordered within a folder, or moved via the tab context menu ("Move to folder / new folder / remove from folder"). Clicking a folder **selects** it (theme-ring highlight) as the target new tabs file into: Cmd+T, link opens, and bookmark opens honour the selected folder (or inherit the active tab's folder via `with_new_tab`), while the explicit "+ New tab" button always makes a **loose** top-level tab (`with_new_loose_tab`). The selection also **tracks the focused tab**: clicking a tab activates it and points the target at that tab's folder (a loose or pinned tab clears it; in the top-tabs strip a click on empty strip space clears it too). This lives in the shared `useFolderTarget` hook (`setTarget` / `syncToTab`) used by `TabList`, `HorizontalTabs`, and `PinnedTabs` so the sidebar and top-tabs behave identically. IDE-style, Enter on a selected folder starts inline rename. Collapsing a folder **sleeps** its member tabs immediately (bypasses the idle timer), tying into the memory model. Commands: `create_tab_folder` / `rename_tab_folder` / `recolor_tab_folder` / `set_tab_folder_collapsed` / `set_tab_folder_icon` / `delete_tab_folder` / `reorder_tab_folders` / `assign_tab_to_folder` / `select_tab_folder`; persisted via migration `M0013` and skipped for ephemeral workspaces (`selected_folder_id` is session-only).
- **Folder + workspace icons**: folders and workspaces can carry an icon rendered inside their colour dot (and beside the island label in top-tabs): a wireframe or filled glyph from the bundled registry (`src/lib/iconGlyphs.tsx`, Lucide-derived closed shapes with wire+fill variants) or an emoji. Encoded as a compact string (`glyph:<name>` | `glyph-fill:<name>` | `emoji:<char>`) validated by the pure `wis_core::icon::parse_icon_ref` at the command boundary (`set_tab_folder_icon` / `set_workspace_icon`); glyph names are charset-checked in core and resolved in the chrome (unknown names fall back to the plain dot). Picked via the shared `IconPicker` (Line/Fill/Emoji tabs + None reset) inside the folder options menu and the workspace recolor expansion. **No migration**: `TabFolder.icon` rides the JSON `tab_folders` column and `Workspace.icon` repurposes the existing, previously unused column. Glyphs tint with `currentColor`; emoji render as-is.
- **History & cookies**: per-workspace deduped history with search (dedupe keys on the **fragment-stripped** URL, so in-page anchor jumps update one row's timestamp/count instead of piling up near-duplicates; different queries stay distinct pages); native cookie/site-data listing and per-domain / full clear via `WKHTTPCookieStore` + `removeDataOfTypes`; unified clear-browsing-data dialog. An untitled page's placeholder title is the bare site name (`wis_core::tab::placeholder_title`, `www.`-stripped host), never the raw URL, in the tab strip, tooltips, and history rows alike.
- **Stay logged in across restarts**: WebKit keeps session cookies (no expiry) only in memory and drops them on quit, so logins like Canvas wouldn't survive a restart. We snapshot a workspace's session cookies (`WKHTTPCookieStore getAllCookies`, expiry-less only) to the `session_cookies` table (after each page load and on a 60s timer) and restore them (`setCookie:`) into the workspace's data store on its first tab each run, before the page loads (`cookies::persist_session_cookies` / `restore_session_cookies`, once per workspace via `AppState::restored_cookies`). Persistent cookies are left to WebKit. Empty snapshots never overwrite a saved one (avoids clobbering a valid session when a store is momentarily released). Never for ephemeral workspaces. **Encrypted at rest**: session cookies are live bearer tokens, so the snapshot is sealed with ChaCha20-Poly1305 (`wis_secrets`) under a dedicated 256-bit key in the login Keychain (`session_key_load_or_create`), distinct from the vault master key and **not** Touch ID gated, so it's available automatically at launch (mirrors Chrome's "Safe Storage"). If the key is unavailable we persist nothing rather than write plaintext; a snapshot that fails to decrypt is treated as "nothing to restore". **Blast-radius bounds**: each snapshot's `created_at` is stamped once (not refreshed by later snapshots), and a restored session **auto-expires after a fixed TTL** (`SESSION_COOKIE_TTL_DAYS` = 14), forcing periodic re-auth so a stolen snapshot is only useful for a bounded window; stale snapshots are purged from disk at launch. The whole feature is gated on the **`persist_sessions`** setting (Settings → Privacy → "Stay logged in across restarts", default on); turning it off skips persist/restore and wipes any saved snapshots.
- **Password vault**: ChaCha20-Poly1305 at rest, master key in the OS key store (macOS Keychain / Windows DPAPI) gated by a biometric (Touch ID / Windows Hello). The gate is a UI re-auth layer (`vault.rs::vault_supported` allows macOS + Windows): the key store protects the key at rest regardless, and the biometric prompt gates the unlock, matching how production browsers layer biometrics over keystore-held keys. On Windows the gate runs only when Hello is **available** (`UserConsentVerifier::CheckAvailabilityAsync`); a machine with no configured PIN/biometric unlocks without a prompt (the key stays DPAPI-sealed) rather than locking the user out, and the consent dialog is shown via the desktop interop (`IUserConsentVerifierInterop` + the foreground window). Save-password capture (native script-message handler -> consent prompt), saved-account picker, and origin-matched autofill (app -> page eval only; pages can't call vault commands). The capture script watches several submit signals (form submit, Enter in a password field, click on a login control, page teardown, and a MutationObserver for the filled password field disappearing) and pierces shadow DOM via `composedPath`, so SPA/modal logins (Twitch, Gmail, Canvas) are caught. Hosts are normalised `www.`-stripped on both save and lookup so the key/autofill match across `www`/bare hosts. URL-bar key button surfaces saved logins; the save prompt persists across the post-login navigation (it follows the captured login in the backend, not the current page host) until the user acts.
- **URL-bar suggestions**: overlay dropdown: recent searches, history-ranked site recommendations, inline base-website completion, favicons. Default search engine setting (DuckDuckGo/Google/Bing).
- **Vendored wry patch** (`vendor/wry`, applied via `[patch.crates-io]`): wry 0.55.1 verbatim except `url_from_webview` no longer unwraps a nil `WKWebView.URL` (clicking "go back" on WebKit's fraud-warning interstitial with an empty back stack panicked inside the navigation delegate and aborted the process). The fix is applied verbatim from upstream PR tauri-apps/wry#1729, so dropping the vendor once that ships is a zero-behavior-change swap. See `vendor/wry/WIS-PATCH.md`. (Kept verbatim deliberately: app features never patch the vendor, so the drop stays clean. The camera/microphone consent feature, for instance, lives entirely in the shell.)
- **Strict CSP on local surfaces** (`tauri.conf.json` `app.security.csp`): the chrome/overlay webviews are the only capability-granting surfaces and render page-controlled strings (titles, URLs, suggestion text), so they carry a strict policy as defense-in-depth behind React's escaping: `default-src 'self'`, `script-src 'self'` (tauri auto-nonces its injected scripts), `img-src 'self' data:` (favicons are data: URLs), `object-src/frame-src 'none'`, `connect-src 'self' ipc: http://ipc.localhost`. `style-src` carries `'unsafe-inline'` (React style attributes); everything else is `'self'`-only because the brand fonts are **bundled locally** (`src/styles/fonts.css` + `fonts/*.woff2`: Geist/Geist Mono primary, Instrument Serif accent, DM Sans/DM Mono fallback, latin+latin-ext subsets, OFL-licensed) - the chrome performs no third-party fetch and renders offline. Applied to assets served via the tauri protocol (production); the vite dev server is uncovered, so verify CSP behavior in a bundled build. `img-src` also allows `wis-asset:` for workspace wallpapers.
- **Fraudulent website warning** (`webview_prefs.rs`): every remote webview (tabs, Peek, widget panels) enables WebKit's `fraudulentWebsiteWarningEnabled` (Apple-proxied Safe Browsing, off by default in WKWebView), showing a full-page warning before suspected phishing/malware sites; complements `link_safety`'s structural heuristics with a real threat database. Settings -> Privacy toggle (default on, since the check performs network lookups); toggling re-applies to all live remote webviews without reloads. Local chrome/overlay webviews are never touched. Tab webviews get a custom **two-finger swipe back/forward with a progress indicator** (`swipe_nav.rs`): the native `allowsBackForwardNavigationGestures` is all-or-nothing and exposes no progress to drive UI, so a builder-level page script watches `wheel` overscroll at the page's *true* horizontal edge (walking the ancestor chain so it never fights a horizontally-scrollable element) and draws a themed half-circle indicator, isolated in a shadow root and drawn in-page for zero IPC latency, that peeks in from the edge as you swipe and, at the commit threshold, **fills** (the arrow flipping from the accent to a contrasting black/white by luminance); on release past threshold it calls `history.back()`/`forward()`, so the URL bar/title sync via the usual page-load hook. The indicator's colour matches the **webview border** (`.kb-content`'s `--primary-400`) and tracks the theme live: the chrome reads its resolved `--primary-400` and pushes it via `set_swipe_accent` (`useSwipeAccentSync`, on every theme/accent change + OS light/dark flip), which stores it on `AppState` (baked into new tab webviews by `accent_script`) and `eval`s it into every live tab webview, so changing the settings theme recolours the indicator immediately. The tab page can't read the chrome's CSS vars itself, hence the push. The baked init script re-runs at every document start, so each navigation reverts `__wisSwipeAccent` to the tab's creation-time value (which is why a back-swipe used to leave the following forward-swipe stale after a theme change); `create_tab_webview`'s `on_page_load` Finished hook therefore re-`eval`s the stored colour after every load. Detection is wheel-based (WebKit exposes no gesture *phase* to JS), so the shell supplies the two signals the script cannot read itself. **Finger lift**: an app-wide `NSEvent` scroll-phase monitor (`install_phase_monitor`, macOS) forwards began/ended transitions to every tab webview, so the gesture commits **exactly at lift** (armed past the threshold) or cancels (below it), and the momentum tail after lift never moves the indicator or re-engages; off macOS a wheel-quiet debounce approximates lift. The indicator is a pure function of the accumulated deltas: it follows the fingers both ways (swiping back below threshold un-fills and disarms) and never animates ahead on its own. **History availability**: `canGoBack`/`canGoForward` are pushed per direction after every load event and title change (`push_nav_state`, macOS + Windows; title changes are the SPA signal, and the in-page `pushState` wrap is definitive; on Windows the flags are read inside the WebView2 `with_webview` hop but the `eval` that pushes them runs **outside** it, since issuing one webview message from within another during a navigation callback re-enters the runtime's inline dispatch and wedges the UI thread), so the gesture only engages toward a direction that can actually navigate. The scroll-vs-gesture call is made **once per wheel sequence** at its first event: a sequence that starts vertical-dominant, over a horizontally-scrollable element, with no history, or **non-cancelable** (the engine already owns that scroll) stays a scroll for its whole lifetime, so an inner carousel reaching its edge mid-swipe can never turn into a navigation. The page itself **never displaces horizontally at the edge**: the script pins `overscroll-behavior-x: none` on the root scroller, since the elastic rubber-band translates the whole viewport layer, `position:fixed` included, visibly detaching the indicator from the edge on fast flings whose early wheel events slip past `preventDefault` (once a sequence's first event goes uncancelled, WebKit delivers the rest non-cancelable); real horizontal scrolling and the vertical rubber-band are untouched. The feel constants live at the top of the script for tuning.

Matching is glob-based (`matches_url`, pragmatic stand-in for Chrome match patterns). - **Video popout**: switching away from a tab that is playing a video floats that video as an always-on-top mini player in its own borderless native window (`video_popout.rs`), free to leave the main browser window and visible on every macOS Space. A second video pipeline is impossible under WKWebView (MSE/DRM streams cannot be re-opened in another webview), so the popout *is the tab's own webview*: `Webview::reparent` moves it into the floating window (and back into the tab's **origin window** on restore, remembered in `ActivePopout.origin_window` and falling back to `main` only if that window has since closed, since with one workspace per window the tab may live in any window; the popout window is also positioned against that origin window's frame; WebKit pauses media on every view-hierarchy move, so each reparent is followed by a page-side resume kick, `__wisPopoutResume`, that retries briefly and never overrides a user-intended pause), an injected script (a **builder-level initialization script** baked into the webview configuration before the first document exists, so an instantly-loading page can never race the injection the way post-creation `addUserScript` calls can) pins the chosen `<video>` across the now-tiny viewport, **reparenting it to the document root while popped** (original slot remembered and restored on exit): with `<html>` as its only ancestor no player wrapper can re-anchor, scale, or crop the fixed pinning (sites have too many ways to create a containing block, e.g. transforms/filters/`contain`, to neutralize one by one), and the whole `<body>` goes visibility-hidden over a black root so a late site restyle can never paint above the video or fade it out, and an injected overlay supplies the controls: an X top right (pauses + dismisses), a hover-revealed **volume cluster** bottom left (speaker toggles the element's mute, a slim slider sets `video.volume`, wheel over it nudges; it mirrors `volumechange`, so the site player's slider and the popout's stay in lockstep both ways, and dragging the slider un-mutes like typical players), click to pause/play (300 ms double-click disambiguation, with a sticky paused glyph), double-click on the left/right third to seek -/+10 s (centre toggles), drag anywhere to move (a single `dragstart` message hands off to native `start_dragging`, so moves are OS-smooth with zero per-frame IPC), and corner zones for aspect-locked resizes (cursor-only affordance like the window edges; the frame math is pure and unit-tested). The popout opens unfocused (never steals typing) yet responds to its very first click: tab webviews are built with `accept_first_mouse`, so a click on a non-key window reaches the page instead of being spent on activation (Chrome-style click-through, applying to background main-window clicks too). The page only reports intents over the narrow `wisPopout` handler; the sender is identified by the WKWebView's stamped `accessibilityIdentifier`, never by page data, and Rust validates every payload, so a hostile page can at worst fiddle with its own popout. The chrome decides *when*, via two triggers. **Automatic**: the injected script tracks the page's dominant qualifying video (unmuted, on-screen, at least 180x100, so muted autoplay ads never trigger) and reports media-state changes (`wis-popout-media`: `playing` gates auto, `present` gates manual); `useVideoPopout` + `useTabWebviews` adopt a tab at its visible-to-hidden transition (tab switch, workspace switch, unsplit; momentary hide-alls like divider drags are flagged transient and skipped, and the active tab is never adopted) and fold it back inline when the tab rejoins the layout. **Manual**: a small pop-out button pinned to the video under the cursor (pointer hit-tested against video rects, since player chrome usually covers the `<video>` element; posts a `request` the chrome re-gates) and the `PopOutVideo` key action (View -> Pop Out Video; **unbound by default**, rebindable in Settings -> Shortcuts; re-triggering folds the popout back). Manual pops work for paused videos too (`present`, not `playing`), ignore the auto setting (explicit intent), and **leave the main window as-is**: the tab keeps its pane, which shows a black player placeholder (`.kb-popout-placeholder`, painted under the native webview so it reveals exactly when the webview departs and can never flash on a failed handshake; clicking it folds the video back). A manual popout never folds back just because its tab is visible; only the X, the placeholder, the key action, a navigation, or closing the tab restores it. One popout at a time; the popped tab is exempt from every sleep path; clicks inside it are player controls, not pane focus (exempted in the `wis-pane-focus` listener); a real navigation or a removed video folds the popout back into a plain hidden webview (pagehide/`lost` message plus a page-load hook as the native fallback); the main window's destruction closes the popout so it can never orphan. The enter handshake is failure-safe: no usable video means the webview simply stays hidden (a 4 s chrome timeout unwinds the attempt). Window sizing derives the height from the video's aspect ratio and tracks it live (a rendition switch or autoplay-next posts the new intrinsic ratio and the window re-locks to it, so `contain` never letterboxes; bars baked into a stream's own pixels, common on cinematic uploads, are content and remain). While popped, the webview carries AppKit's width+height-sizable **autoresizing mask**, so the OS itself keeps it exactly filling the window through every resize, synchronously and immune to cross-thread bounds-message timing (the runtime's rate-based auto-resize and explicit per-message sizing both accumulate visible error at larger sizes); the mask is cleared on restore since the chrome owns main-window bounds explicitly. **Every popout starts at the predefined default size** (440 logical px wide, height from the aspect); only the position persists, in `localStorage`; a fresh popout docks at the main window's bottom-right and every frame clamps into the monitor work area. The automatic trigger is gated by `UserSettings.video_popout_enabled` (default on, Settings -> Layout; settings blob, no migration). Known scope: main-frame videos only (cross-origin iframe embeds don't pop out), and the X pauses before dismissing so audio never plays invisibly.

- **Downloads**: file downloads from remote webviews (tabs, Peek, widget panels) are intercepted via wry's download hook (`downloads.rs`) and handled safety-first. The destination is always `~/Downloads/<leaf>`: the server-suggested filename is reduced to a safe leaf by `wis_core::sanitize_filename` (final path component only, no control chars/`:`/leading dots, length-capped) and collision-resolved Finder-style by `unique_filename` against both disk and in-flight downloads, never overwriting; a destination that would escape the downloads directory is denied outright. Completed files are tagged with the `com.apple.quarantine` xattr so Gatekeeper scans them like any browser download. Items (`DownloadItem`: url, path, received bytes, status, private flag) live in `AppState.downloads` (sync mutex, since wry's callbacks are synchronous main-thread code); every change emits `downloads-changed` and the chrome refetches via `list_downloads`. macOS API limits (WKDownload through wry): the finish event carries only url+success, so completion matches the oldest in-flight download of that URL; there is no native progress or cancel callback, so progress is the destination file's growing size polled every 500 ms (total size unknown, indeterminate). Downloads from a private workspace or Peek still save (user-requested) but are flagged `private` and never recorded in persistent history. **Completed downloads persist** across restarts in the `downloads` table (append-only, global, `M0014`): a successful non-private finish writes its row off the main thread, `list_downloads` returns this session's items (all statuses) merged with prior sessions' completed history (deduplicated by id), and `remove_download` drops an entry from both the list and the table without touching the file. Engine-created popups (`window.open` allowed via `on_new_window`) carry no wry delegates, so downloads inside them are not intercepted. **UI**: a downloads glyph sits in both layouts (sidebar footer cluster and the top-tabs rail controls), with a pulsing accent dot while anything is in flight; it toggles the `overlay-downloads` popup (`DownloadsMenuSurface`, bookmarks-popup styling incl. the liquid-glass toggle) showing the latest entries: in-flight rows with an indeterminate progress bar and live byte count (no total is available, see above), completed rows that **open the file on click** and show "File may have been moved or deleted" when it is gone, an X to remove an entry, and a "View all downloads" footer that opens the full page. The full page (`about:downloads` -> `DownloadsPage`, history-page styling) adds search (client-side over filename/url/host), per-row open + "Show in Finder" + remove, day grouping, and a select mode (checkboxes, select all) whose Delete asks for confirmation (red button) and removes only history entries, never files. `open_download`/`reveal_download` validate before shelling out (`open`/`open -R`): the id's recorded path must still exist as a regular file resolving directly inside its recorded directory (anchoring on the recorded parent covers custom ask-where locations while still ruling out symlink swaps); a missing file resolves `false` (the moved-or-deleted notice) rather than erroring. **Ask where to save** (Settings -> Downloads, `download_ask_where`, default off): each download runs a native `NSSavePanel` (synchronously inside wry's main-thread download callback via `runModal`) prefilled with the sanitised suggested name and starting in the **remembered last-picked directory** (`download_last_dir`, updated only by panel picks and persisted through the normal settings path); cancel denies the download, and a panel-confirmed replace deletes the existing file first since WKDownload refuses an existing destination (an explicit user gesture, so the never-overwrite rule for server-driven names is not weakened). The download callback reads these settings through `AppState.download_prefs`, a sync mirror seeded at startup and refreshed by `update_settings`, because the synchronous callback cannot await the `BrowserState` lock.

Clicking one opens the site in its **widget panel** (`widget_panel.rs`): a per-widget, per-window webview (`widget-panel-<window>-<id>`, id validated before becoming a label; scoping by window keeps each OS window's panels distinct so the same widget can be open in two windows) floating above the tab webviews on the rail-nearest side (Opera-style), modeled on Peek but sharing the **calling window's workspace data store** (logins persist; ephemeral workspaces get incognito), that workspace's proxy, the A1 user agent, and the same `WKContentRuleList` filtering as tabs; no Tauri capability. A **freshly created** panel is built at `about:blank` (showing only its grey backing) and slides in idle, then loads the real page after the entrance (`WIDGET_ENTRANCE_MS`, matching the chrome's `PANEL_ANIM_MS`), so the page's heavy first paint never janks the slide; the panel webview's grey is applied (and awaited via a channel) before the first `show()` so the reveal is never an unstyled flash. **Switching widgets is a hide/show of already-loaded webviews, not a navigation**, so it is instant and each widget keeps its own in-page state; the pool is bounded by a **user-set limit** (`widget_panel_limit_enabled` / `widget_panel_limit` in `UserSettings`, default 2, LRU-evicting hidden ones since each is a full page worth 100 MB to ~2 GB for heavy apps like WhatsApp Web; the toggle off means limitless, and limit changes apply immediately: lowering the cap or re-enabling it trims the pool on the spot). **Keep-loaded is itself a setting** (`widget_keep_loaded`, default on): off destroys a panel's webview the moment it is dismissed or switched away from, reclaiming its WebContent process immediately (logins persist in the workspace data store; reopening reloads). When kept loaded, hidden panels are reclaimed after a widget-specific idle window (`widget_sleep_minutes`, default 5, decoupled from the tab-sleep setting it previously inherited), and a **memory-pressure cap** (`widget_memory_cap_enabled`/`widget_memory_cap_mb`, default 500 MB) sweeps every 30s via `list_webview_memory`, evicting hidden panels oldest-first whenever their combined WebContent footprint exceeds the cap (size-based companion to the count cap: one WhatsApp Web outweighs several light panels). Settings -> Performance hosts the limit toggle + count, plus the **loaded panels readout** (`list_widget_panels` + the `widget-panels-changed` event emitted on create/destroy) with a "Close all" reclaim button. In collapsible sidebars and the top-tabs rail the dock is anchored to the pinned edge at the collapsed band width, where its width-bound rows wrap the icons into a vertical column; expanding the sidebar/rail releases the row width (transitioned), re-flowing the icons into the horizontal social/AI rows, and the divider lines stretch across the expanded width and shrink back on collapse. A collapsed sidebar also expands whenever the cursor reaches the window's outermost edge column (document-level mousemove; the in-aside hot strip alone misses the first pixels because the window-resize handles sit on top of them). **Resizing**: native webviews swallow pointer events, so the drag handle is the `overlay-widgetresize` surface (`WidgetResizeSurface`), an invisible full-height strip straddling the panel's inner edge in a thin overlay webview (overlays are promoted above all webviews; the panel re-promotes them on creation). Like the window resize edges, the affordance is the `col-resize` cursor, not a visible handle. **Stacking is actively maintained** (tabs < panels < overlays): tab webviews are created lazily and each `add_child` lands on top of everything, so `create_tab_webview` re-promotes panels then overlays (`promote_panels_to_front`), and re-showing a hidden panel re-promotes too (its stale subview position may have been overtaken). An accent **header bar** (`overlay-widgetheader`, `WidgetHeaderSurface`) docks above the visible panel with the widget's **current host** on the left and a **mute** toggle + **reload** button (top right): native cache-bypassing `reloadFromOrigin` via `reload_widget_panel`, so a hung page (which would never run injected JS) still recovers; the bar tracks the panel live during resize drags. The host is read-only, derived from the panel's live URL: the panel webview reports each main-frame navigation (`on_page_load` Started -> `wis-wpanel-nav` `{ id, url }`), `useWidgetPanel` caches it per widget and pushes it to the header with the mute state (`wis-wpanel-state` `{ muted, url }`) on every show, navigation, and toggle, so a widget that redirects shows where it actually went. The panel webview draws no engine background (`drawsBackground = NO`) but its **layer carries the theme surface colour** (passed as `dark` at open time, mirroring `--surface-raised`): tab webviews stack between the chrome and the panel, so the chrome-layer backdrop card (`.kb-wpanel-backdrop`, still rendered for chrome pages and resize strips) cannot show through on remote pages, and a fully transparent panel would flash the page beneath until the widget paints. `window.open` popups are **allowed** like tab webviews (OAuth "Sign in with Google/Apple" flows otherwise dead-end or strand an invisible child webview). Theme-sensitive widget URLs go through `effectiveWidgetUrl` (Instagram's web dark mode is a `?theme=dark` query parameter, not `prefers-color-scheme`): applied at open time, and a live light/dark flip re-navigates affected panels immediately (`navigate_widget_panel`, watched via a `data-mode` MutationObserver in `useWidgetPanel`). The surface emits drag deltas (`wis-wresize-*` events); the chrome resizes the panel live anchored at its outer edge and persists the width in `localStorage` (clamped 300px..55vw). Dock favicons can be **drag-reordered** within their row (pointer-based, like tabs; HTML5 DnD is swallowed in the main chrome webview); the persisted `sidebar_widgets` order is the display order. It is **not a tab**: a panel dismisses on re-click, Escape, any chrome click outside the dock, a click inside a tab webview (native `wis-pane-focus`), or an active tab change (`useWidgetPanel`). Dismissal **hides** the webview rather than destroying it, so re-opening is instant with in-page state (drafts, scroll, live connections) kept; hiding also **suspends all media playback** in the panel (`setAllMediaPlaybackSuspended`, macOS 11.3+ public API, selector-guarded; resumed on re-show), so a backgrounded panel keeps its sockets but never keeps video/audio decoders running; guardrails: the calling window's panels hard-destroyed on workspace switch (`close_all_widget_panels` is window-scoped; each is bound to one workspace's data store + proxy), dismissal destroys outright in private workspaces, and a panel left hidden past the widget idle window (`widget_sleep_minutes`) is destroyed to reclaim memory. Favicons via `prefetch_favicon`, prefetched at startup and cached in-memory + on disk (`WidgetFavicon`, letter-tile fallback). Chosen in Settings -> Sidebar widgets (toggle chips, social / AI groups). Global across workspaces; stored in the settings JSON blob (`#[serde(default)]`, no migration). Rendered in all layouts: sidebar docks show two horizontal rows; the top-tabs rail shows a centred vertical column above the rail controls. Favicon capture falls back to the page's `<link rel="icon">` declarations (hand-rolled scanner in `favicons.rs`, no HTML-parser dep) when `<origin>/favicon.ico` yields no usable image, which is how Discord, Gemini, DeepSeek and most SPAs expose icons.
- **Per-workspace backgrounds**: each workspace can carry a custom page background (`Workspace.background: Option<Background>`, `wis_core::background`, persisted as JSON via `M0015`; ephemeral workspaces keep it in memory only). Gradients ship first: a `GradientSpec` (angle + 2..8 hex stops, validated at the IPC boundary before entering state) edited live from Settings -> Appearance -> Workspace background (`BackgroundEditor`, acting on the active workspace; the mode selector grows to gradient/image/GIF when wallpapers land) (preview, angle slider + typed degrees capped 0..=180 since larger angles mirror smaller ones, per-stop **custom colour picker** (`ColorPicker` in `controls.tsx`, hand-rolled SV square + hue slider + hex field, no library), add/remove stops, "Theme default" reset; edits debounce 150 ms into `set_workspace_background`). Rendering overrides the `--wp-grad` token on `<body>` (`useWorkspaceBackground`), which already drives the launchpad page, so a gradient themes the page with zero component changes. **Wallpapers/GIFs**: the same Settings menu carries a Theme/Gradient/Image mode selector; Image opens a native `NSOpenPanel` (main-thread `runModal` via `run_on_main_thread`), and `import_wallpaper` validates by **magic bytes only** (png/jpeg/gif/webp), caps files at 20 MB, and stores them content-addressed as `<app_data>/wallpapers/<sha256>.<ext>` (favicon-store pattern; re-import dedupes). `Background::Image { asset, fit, dim, blur }` renders through the `wis-asset://wallpaper/<hash>` protocol (registered app-wide but answering **only** `main`/`overlay-*` labels with immutable cache headers; the hash is strictly 64 hex chars so requests cannot address outside the store; `wis-asset:` added to the CSP `img-src`). The launchpad paints images as a **shared canvas**: the backdrop pseudo-layers span the whole content host (each pane measures its slice offset in `NewTabPage` and the pane clips the layer), so split panes reveal contiguous regions of one wallpaper laid out against the full content area, coverage holds for any pane shape, and blur seams line up across panes; a blurred cover fill sits underneath so contain/tile letterboxes land on a blurred copy of the wallpaper, never a bare strip. The blur control (0..=40 px) blurs the wallpaper without blurring content; fit maps to cover/contain/tile (applied against the host box) and dim (0..=80%) layers a black overlay; GIFs animate natively. Each mode's last configuration **persists** (`Workspace.background_drafts`, updated by `with_background`, `M0017`), so switching Theme/Gradient/Image restores what the user built in each, across restarts. Separately, the workspace popover's accent grid ends with the saved **custom colour palette** (`UserSettings.custom_accent_palette`, shared across workspaces, settings blob) plus a dashed `+` square: clicking it spawns a tentative swatch with the colour picker open, Esc/click-away discards it, and only the picker's `+` confirm saves the colour to the palette and applies it to the workspace (`Workspace.custom_accent`, validated hex, `M0016`, painting the dot and clearing when a preset is picked).
- **Custom themes**: full chrome themes built in Settings -> Appearance -> Themes (`ThemesSection`). A `CustomTheme` carries light+dark `ModeTokens` (accent + bg/surface/raised/chrome/content/text/secondary/border, all boundary-validated hex via `wis_core::theme`); the accent expands into the whole `--primary-50..900` scale at apply time (`src/lib/theme.ts` `themeVars`, pure mixes toward white/black). Activation (`set_active_theme`, validated against the stored list) injects the vars inline on `<body>` in `useThemeApply` (inline beats the `[data-accent]`/`[data-mode]` rules), so the entire chrome re-themes with zero component changes and reverts cleanly to the built-in presets. Stored in `UserSettings` (`custom_themes` + `active_theme`, settings blob, no migration); list edits replace-whole through the settings patch and are re-validated in `update_settings`. Editor: per-mode colour pickers with live apply (debounced), new, duplicate, delete (confirm). **Sharing**: `export_theme`/`import_theme` move versioned `.wistheme` JSON via the shared native panels (`panels.rs`, main-thread `runModal` dispatch); import size-caps the file, validates the full structure, rejects newer-versioned files, and re-mints the id so a shared theme can never collide with an existing one.
- **Motion**: all chrome transitions draw from central motion tokens in `tokens.css` (`--dur-fast/med/slow`, `--ease-standard`, `--ease-emphasized` springy, `--ease-exit`; the scattered hardcoded durations/beziers in `window.css` were folded into them). A three-tier `UserSettings.motion` (`MotionLevel`: Full/Reduced/Off, settings blob, no migration; Settings -> Appearance segmented) maps to body classes in `useThemeApply`: **Reduced** keeps every duration but flattens `--ease-emphasized` to standard (no overshoot), **Off** zeroes transition/animation durations inside the chrome, and the OS `prefers-reduced-motion` preference caps Full at Reduced live. Drag-reorder choreography builds on these tokens (`lib/tabMotion.ts`): while a drag is in flight the source element keeps its slot hidden under the floating ghost and siblings **live-part** one slot around the insertion point (transform transitions gated by `body.is-tab-dragging`; covers sidebar rows, sidebar folder rows, top-strip loose tabs, pinned circles and folder islands, replacing the old insertion-line indicators); insertion hit-testing measures **parting-free layout rects** (`layoutRect` in `useTabSplit`, the live rect minus the element's transform): hit-testing the transformed rects made the boundary chase the pointer and the drop index oscillate between neighbours (visible drag jitter on pinned circles and islands); loose insertion also never targets the islands/pinned block (`overFixedCells`), and loose tabs keep their flex-grow share during an in-loose reorder so the row doesn't shrink to bare basis the moment a drag starts; tabs reorder **within folders** in both layouts, and a tab dragged from outside an open folder (or out of one, over the loose list) targets a **positional slot** (`insertedAmong`: assign + reorder in one drop; expanded islands widen by one slot while targeted); reorders and folder assignment apply **optimistically** (`patchTabOrder`/`patchFolderOrder` cache patches) so the drop re-renders in the new order on the same frame, and the dropped element then **glides from the ghost's rect into its slot** with a small settle pop (WAAPI; pop dropped on Reduced, skipped on Off). The sidebar's active-tab marker is a single sliding bar (`.kb-active-bar`, measured against the list root, re-measured when folder folds land) instead of a per-row `::after`; the settings section nav uses the same pattern (`.kb-settings-nav-ind` pill gliding between items). **Workspace switches** slide the tab list/strip in from the side of the new workspace's position relative to the old (`workspaceSlideIn`, imperative WAAPI, no remount). **Peek grows from the clicked link**: the Opt+click script forwards the click point, the chrome translates it to window coords against the content host (approximate in split layouts), and the card scales up from that transform-origin, with the native preview created only after the grow so it never composites over the animating card. The **downloads popup** rises in with its rows following on a small stagger, replayed per open via a shown-event nonce. The top strip reflows loose-tab widths through a flex group anchored to the corner opposite the rail, so folder collapse/expand (sized as collapsed from the closing frame, width contracting in step with the shrink sweep), spawns and closes glide without ever moving the folders or pinned circles; folder islands and loose tabs flow together in one corner-anchored scrollable run (`.h-strip-run`; the strip itself never scrolls), so overflow scrolls the run (islands included) while the **pinned circles stay anchored at all costs**; activating a tab centres it within the run, and the sizing maths recompute on every change, so the bar never shows dead space (under-fill grows the loose tabs back to fill the row, overflow scrolls a full viewport). **Closing a tab is a FLIP glide**, not a collapsing slot. The instant a tab closes it is dropped from the sizing inputs *and* taken out of the layout entirely (`.h-tab.is-closing` is `display: none`), so its slot *and* its inter-tab gap are gone on the close frame, the survivors' new positions are the true n-1 layout, and the tab count drops at once; there is never a shrinking sliver or a leftover gap blocking the resize. The survivors then **glide from their old slots into the freed space**: just before the close the strip snapshots every sizable tab's rect (`captureFlip`), and a layout effect maps each survivor back to its captured rect with a left-anchored `translateX` + `scaleX` and animates to the identity via the Web Animations API (First-Last-Invert-Play). Animating position *and* width together (linearly, so left edges and widths interpolate in lockstep) keeps neighbours tiled at every frame then they glide as one into the new layout. The duration is read off the live computed `--reflow-dur` (so motion-Off, where it is `0s`, skips the glide and snaps). While a close is in flight the strip uses the faster `--dur-fast` (`.is-tab-closing`). Closing a tab while a previous glide is still running **cancels the in-flight FLIP** (the animations carry an id so they can be found) and starts one fresh pass from the current position, so the ease never replays on top of itself. The close is also **deduped per id**: `closeTabAnimated` broadcasts on both the DOM and Tauri channels, so `onTabClosing` fires twice for a same-webview close; a guard set ensures the snapshot + mark run once (the echo's stale snapshot would otherwise replay as a phantom glide at the 580ms retire). A **folder island** whose member closes shrinks the same way: the closing member is dropped from the island's width (so the pill has no hole where the `display: none` member sat) and the pill's `flex-basis` glides shut on the same fast linear clock as the members' FLIP, so the background closes in step rather than snapping. The closing tab stays in the list as a `display: none` ghost until it is retired ~580ms later (the lifetime that bridges the IPC refetch); since it occupies no layout, retiring it shifts nothing. (A zero-width-with-negative-margin tab was tried first but left a stray gap, since WebKit does not fully cancel a flex `gap` with a negative margin.) **Closing the *active* tab** is the one resize that would otherwise still lag, because the promoted tab grows to the larger active width only once `active_tab_id` updates on the refetch: the strip predicts the promotion locally (`lib/paneActive.ts`, a pure mirror of `Workspace::with_tab_removed` *then* `with_pane_after_removed` plus `PaneNode`) and sizes + highlights against it immediately, so it glides in *with* the close. The prediction covers both layouts so it never jumps on the refetch. The whole close is also **triggered synchronously**: the strip's own close button/middle-click mark the tab closing on the gesture frame, and `closeTabAnimated` broadcasts on a synchronous in-document DOM event (caught same-tick by both strips) as well as the cross-webview Tauri event, so the exit + reflow begin immediately instead of after the event round-trips through the backend (that latency was a visible pause between the webview vanishing and the strip reacting). Expanded-island **members are capped** (`MEMBER_TAB_MAX` 150 / 120 compact; the active member caps at the active-tab floor instead) rather than keeping the loose tabs' equal share, so filing a tab (drag, menu move, or move-to-new-folder) visibly compacts it into the pill and the loose tabs absorb the slack; with no loose tabs left, capped islands leave intentional whitespace instead of stretching. The strip is also an **accordion**: at most `UserSettings.top_tabs_max_expanded_folders` islands stay expanded at once (default 2, `0` = no limit, segmented 1/2/3/No limit in Settings -> Layout, settings blob, no migration); expanding one past the limit collapses the least-recently-expanded island with the usual exit sweep (recency is session-scoped per workspace, seeded in position order). Enforced only in the top-tabs UI at expand time; the sidebar tree is unrestricted, folders never auto-collapse under ambient pressure, and a collapse triggered this way sleeps the folder's members like any other collapse. **Native surfaces animate by stepping webview bounds per frame over IPC**: animations never resize a live page (reflow-per-frame reads as jank). **Split entrances are a chrome-side glide**: when a split adds a pane while others persist, the webviews tuck away for ~300ms (the same preview look as divider drags), the mounting `PaneSplit` starts the new leaf's slot at zero and glides it open via a flex-grow transition (`.is-entering`, `PANE_GLIDE_MS`), then the webviews reveal at their final rects (`TabWebViewHost` diffs the leaf set during render so the same commit both arms the entrance and tucks the webviews; workspace switches and replacements stay direct). **Removals mirror it**: closing a pane or unsplitting (Cmd+Opt+U) keeps painting the outgoing tree (render-phase state adjustment, so the new tree never flashes) while every split whose entire subtree is being removed glides that slot shut (`.is-exiting`, `subtreeCloses`), then the committed tree takes over and the webviews reveal. The **widget panel** slides in from the dock edge at full size on a plain ease-out (no spring), the header bar tracking the same offset via raw bounds writes; the chrome backdrop plays a matching CSS slide (capped 48px on both sides so panel and backdrop stay congruent), and create paths animate only header + backdrop since the native panel reveals itself at full size on load (`useWidgetPanel`).
- **Theme mode**: the Light/Dark/System setting drives the chrome via `data-mode` (CSS) and is also pushed to **web content**: each tab webview's native appearance is overridden (macOS `NSAppearance` DarkAqua/Aqua, or cleared for System; on Windows the WebView2 profile's `PreferredColorScheme` is set Dark/Light/Auto via `ICoreWebView2_13::Profile`, which is per-profile so every tab shares it, matching Wis theming all tabs alike) so a page's `prefers-color-scheme` matches the in-app theme instead of the OS (`apply_tab_appearance` on tab creation; `apply_appearance_to_all_tabs` on theme change).
- **Peek**: Opt+click (intercepted at `mousedown`, since macOS turns Option+click into a download) a link to preview it in a small isolated card without leaving the page. The preview (`peek-page-<window>`, per-window so each OS window previews independently) is incognito (separate ephemeral data store) and routed through the calling window's workspace proxy, so a link-based scam can't touch the browser; a banner warns about suspicious links via pure heuristics (`wis_core::link_safety::assess_link`: homograph/punycode, `user@host`, deceptive anchor text, IP host, http, etc.). A reader toggle transforms the page in place inside the isolated view (the same `reader::reader_script` transform that backs full-page reader mode). Trigger is a narrow `WKScriptMessageHandler` (`wisPeek`) plus an Opt+click detector script **baked into the tab webview at builder level** (an `initialization_script`, like the video-popout pin, via `peek::page_script`): added post-creation as a `WKUserScript` it would miss whatever page was already loading, so the first page after a fresh launch could not be peeked until a reload. The card is the `overlay-peek` surface with the live page tiled into a measured hole. Opening a High-risk link "as a tab" first requires confirming a red "Proceed anyway" dialog.
- **Reader mode** (`reader.rs`, `tab_set_reader` command): a clean-article view for the active tab, toggled from the toolbar (the reader glyph next to refresh), the `ToggleReader` key action (`Alt+Cmd+R`, View -> Reader Mode, rebindable), or the command palette. The transform (`reader::reader_script`, shared with Peek) runs **inside the tab's own webview** (rebuilds the document tree by assigning `documentElement.innerHTML` with the extracted article; **not** `document.write`, which WebKit silently leaves blank on some pages, e.g. Wikipedia), so no untrusted markup reaches the chrome; exiting reloads the live page. A session-only `Tab.reader` flag (in-memory like `loading`, reconstructed `false` on load) drives the toolbar button's active state; a real navigation resets it via the page-load `Started` handler. Disabled on chrome pages (Settings/History/new-tab).
- **Page capture** (`screenshot.rs`, macOS): a capture **copies to the clipboard by default** and a small success toast then offers a **Save** to write it to disk. `capture_to_clipboard(id, mode)` (`mode` = `visible` tab content / `region` drag-select / `window` the whole browser frame) snapshots, copies the PNG to the pasteboard (`NSPasteboard writeObjects`), and stashes the bytes in `AppState::last_screenshot`; `save_last_screenshot` runs the native `run_save_panel` over those bytes (so Save never re-captures). **Window capture** composites the browser as it appears **without Screen Recording permission** (deliberately, for a privacy browser): `capture_window` snapshots the calling window's chrome webview (the injected `chrome: Webview`) as the base layer, then snapshots every visible `tab-*` webview of that window and draws them over it into one window-sized `NSBitmapImageRep` (`NSGraphicsContext`), each layer placed at its frame in the content view (`convertRect:fromView:`, with a flipped-origin adjustment) scaled by `backingScaleFactor`. Each tab layer is **clipped to its on-screen corner radius** (read from the webview layer's `cornerRadius`, which `set_webview_corner_radius` set; `takeSnapshot` itself returns a square image) via an `NSBezierPath` rounded-rect clip, so the composited panes keep their rounded corners against the chrome behind them. Native titlebar buttons and transient overlay popups are not part of the composite. Window capture works on chrome pages too (their content is in the chrome webview). Capture uses WKWebView's `takeSnapshotWithConfiguration:completionHandler:` (macOS 11+) on the main thread via `with_webview`, the async completion bridged over an mpsc channel (the same `RcBlock` pattern as `biometrics`); the `NSImage` is encoded to PNG via `NSBitmapImageRep` (at backing scale, so captures are retina-sharp). The **region (drag-select)** mode is **window-level** (the selection can include the chrome, not just the page): the `capture_region` action opens a full-window `overlay-screenshot-region` webview (`ScreenshotRegionSurface`, orchestrated by `useScreenshotRegionOverlay`) that composites **above the tab webviews**, dims the window, and lets the user drag a theme-accent (`var(--primary-400)`) rectangle; the drag **captures the pointer** (a stray release outside the window still resolves, clamped) and the surface takes **first-responder focus** so **Escape cancels**. On a result the chrome calls `capture_to_clipboard(.., Region, rect)`, where `rect` (content-area top-left CSS px) is passed to `capture_window` as a `crop`: the composite is built at the crop size with each layer shifted so the cropped sub-region maps to the output origin (the selection overlay itself is a separate webview, never part of the composite). The same path serves whole-window and region capture, so a region can faithfully span toolbar/sidebar and page. Three rebindable key actions (`CaptureVisible` / `CaptureRegion` / `CaptureWindow`, **unbound by default**) surface in the File menu and command palette; visible/region are inert on chrome pages (no `tab-*` webview to snapshot) while window capture works anywhere. The success toast is the `overlay-screenshot-toast` overlay webview (`ScreenshotToastSurface`, orchestrated by `useScreenshotToastOverlay`): it drops down at the window's top-right, says "Copied to clipboard", auto-dismisses after ~3s (paused while hovered) and reverses out, and its Save button reuses the sidebar downloads icon (`DownloadIcon`); a surface-ready handshake replays the first "shown" that races the lazily-created webview. **Cross-platform**: on Windows the **visible** mode captures the tab viewport via WebView2's async `CapturePreview` (PNG stream drained on the UI thread; `imp_win`), decodes the PNG (`png` crate) to RGBA and copies it to the clipboard through `arboard`'s image support, and `save_last_screenshot` shares the now cross-platform `run_save_panel` (`rfd`). Window/region **composite** capture has no WebView2 equivalent (nothing snapshots the chrome + overlays as one image), so those modes stay macOS-only and return a clear error there; **Linux** viewport capture (WebKitGTK `WebView::snapshot`) is not yet wired (its save + clipboard path is ready, only the capture call remains). The capture is held for Save even when the clipboard write fails.
- **Encrypted profile backup** (`backup.rs`, Settings -> Backup & restore): export selected categories to a passphrase-encrypted `.wisbackup` file and restore one by merging it in, to move a profile between machines (local-first, no server). The payload shape, boundary validation, and id re-mint live in `wis_core::backup` (`BackupPayload`, each category an `Option`); the file is a versioned envelope whose payload is sealed with **ChaCha20-Poly1305 under an Argon2id passphrase-derived key** (`wis_secrets::derive_passphrase_key` + `random_salt`, distinct from the device-bound Keychain master key so a bundle is portable). `export_backup(passphrase, options)` snapshots the toggled categories, encrypts, and writes via the native save panel; `import_backup(passphrase)` reads + AEAD-decrypts (a wrong passphrase or tampered file fails to open), validates, **re-mints ids**, applies the profile graph natively, and returns an `ImportSummary` (settings + counts) for the chrome to finish. Categories (per-export toggles): **settings/themes** (applied via the existing settings commands, reusing their validation + side effects: menu rebuild, theme apply); **workspaces + tabs + bookmarks** and (separate toggle) **browsing history**. The whole workspace graph is re-minted in `wis_core::backup` (`reminted` regenerates workspace/tab/folder ids and remaps `tab_order`, `pinned_tab_ids`, `active_tab_id`, the pane tree, and bookmark/history workspace keys); `merge_profile` then splices the non-clashing workspaces + their tabs into the live `BrowserState` (immediate write), and the shell re-creates each added workspace's bookmark folders + bookmarks and re-records its history through `Storage`. Import is **merge, not replace**: imported custom themes append only when not already present **by name + content** (deduped, so a self-import never piles up duplicates), and a workspace is **skipped when its name already exists** (so a re-import is a no-op for the graph). Private/ephemeral workspaces are never exported. The **saved-passwords** category (opt-in) is the only part needing the device's vault key: on export `vault::export_credentials` unlocks the vault (Touch ID), decrypts each stored password with the device master key, and places it **plaintext inside the passphrase-sealed payload**; on import `vault::import_credentials` unlocks (Touch ID) and **re-encrypts each under the new device's master key**, upserting by `(host, username)` (no duplicates). Passwords are applied **before** the profile, so declining Touch ID aborts the import before anything is written.
- **Configurable launchpad + homepage** (`wis_core::new_tab`, Settings -> New tab): the launchpad's shortcut tiles are user-editable (`UserSettings.shortcuts: Vec<ShortcutTile>`, default a 5-site starter set), and `new_tab_target` (`Launchpad` | `Homepage`) chooses what a freshly opened tab lands on, with the homepage taken from the existing `UserSettings.homepage`. The launchpad reads `settings.shortcuts` (favicon-cached tiles, letter fallback cycling `FALLBACK_CLASSES`); the explicit `+` button and Cmd+T resolve their URL via `resolveNewTabUrl(settings)` (homepage when chosen and set, else `about:blank`), while splits, private windows, and new-workspace first tabs stay on the launchpad. Tiles are **drag-reorderable on both surfaces** (the launchpad and the Settings list) via `usePointerReorder` (pointer-based, since HTML5 DnD is swallowed in the main chrome webview), which reuses the **tab-strip drag choreography** (`lib/tabMotion`): a clone of the grabbed tile floats under the cursor (`kb-drag-ghost`), siblings part to make room (`partOffset`, the grabbed item keeps its now-invisible slot so parted siblings pre-occupy their final positions), and on release the dropped tile glides from the ghost into its committed slot (`glideIntoPlace` via a `pendingGlide` consumed in a layout effect). The new order commits to `settings.shortcuts` (optimistic, so it lands instantly), keyed by tile URL (`lib/shortcuts::reorderByKeys`). On the launchpad a press-drag is disambiguated from a click (so a tile still navigates on a plain click); the Settings list uses a dedicated grip handle. All values are **sanitized at the IPC boundary** in `update_settings` via pure core helpers (`sanitize_homepage`, `sanitize_shortcuts`): http(s) only (a non-web scheme like `mailto:`/`javascript:` is never re-schemed to https and smuggled through), labels trimmed (host-derived when empty), deduped by URL, capped at `MAX_SHORTCUTS` (8). Settings persists in the JSON blob (`#[serde(default)]`, no migration).
- **Navigation safety interstitial** (`navguard.rs` + `overlay-navguard`): complements Peek for *real* navigations, with two layers: (1) a narrow `wisNavGuard` handler + injected script intercepts a plain (non-Option) left-click on a risky link **before it navigates** (`preventDefault`), so nothing loads in the background (`navigated: false` → "Take me back" just dismisses); (2) a page-load fallback (`maybe_guard` on `on_page_load` Started) catches anything the click path can't (address bar, JS redirects), halting the load via `stopLoading` (`navigated: true` → "Take me back" goes back). Rust re-assesses the href; for High (and non-`insecure_http` Medium) hosts not already waved through (`AppState::nav_guard_bypass`, session-scoped) it raises a full-window interstitial with threat level + reasons, "Take me back", and a red "Proceed anyway" (navigates + remembers the host). HTTPS-First means plain-`http` Medium is intentionally not interrupted. The `deceptive_text` heuristic (anchor text naming a different site than the href) only treats bare dotted text as a domain when its final label is a recognised TLD (`wis_core::link_safety::TEXT_DOMAIN_TLDS`, baked into the JS pre-filter so both gates agree), so dotted filenames as link text ("README.md" in a GitHub file list, "Cargo.toml") never flag; explicit `https://...` text bypasses the gate. Same-page fragment clicks (pure `#` jumps) are skipped by the interceptor.
- **Bookmarks**: per-workspace, organised into optional folders (`folder_id` NULL = unfiled, rendered loose, no auto "Unfiled" folder), persisted in SQLite (`wis_storage::bookmarks`, never in `BrowserState`). A bookmarks glyph (sidebar footer cluster / top-tabs rail control, styled like the VPN/settings circles) opens a palette-style overlay popup (`overlay-bookmarks`, liquid glass, aligned to the sidebar side) showing unfiled bookmarks as favicon bubbles, then folders that expand to indented favicons; folder create/rename/delete are inline (delete re-parents to unfiled). The address-bar **star** bookmarks the page into the last-used folder (persisted per workspace in `localStorage`, default unfiled) and **auto-pins** it to the quick-access row while that row has room (`PIN_CAP` = 6 = one row), then opens an anchored folder picker (`overlay-bmpicker`, vault-menu style) to confirm/change the folder; clicking the star again removes the bookmark. Disabled in private (ephemeral) workspaces. **Pinning is independent of folder membership** (`pinned`/`pin_position` columns): a bookmark can be pinned to the quick-access grid *and* live in a folder, appearing in both. The popup renders the **pinned quick-access grid** (every `pinned` bookmark, ordered by `pin_position`), then folders that show all their bookmarks (including pinned ones), then the **unfiled-and-unpinned** rest list below the folders. Every bookmark mutation broadcasts a `bookmarks-changed` Tauri event and each webview (main-chrome star, popup, picker, with separate React Query caches) refetches via `useBookmarkSync`, so moves/pins/edits stay in sync across surfaces. The popup also optimistically patches its own React Query cache on each mutation (`setQueryData`) so the open popup updates instantly without waiting on the refetch (which otherwise lags for in-popup folder create/rename/delete). The popup's queries are keyed by the active workspace and gated only on it (no `visible` flag: the overlay webview persists, so a visibility flag set once on mount would never re-enable on reopen and the popup would show stale/empty data); opening the popup re-emits `browser-state-changed` + `bookmarks-changed` so it tracks the current workspace (e.g. after adding/switching one) and shows fresh bookmarks. In the popup, favicons can be **dragged onto a folder** (`move_bookmark`, keeps the pin), **dragged onto the unfiled area below the folders** to take them out of a folder (unfiles **and** unpins, since that area lists plain unfiled+unpinned bookmarks, so the favicon lands where it was dropped instead of staying a bubble), **dragged onto the pinned grid** (pin: add while the row has room, or drop on a bubble to replace it when the row is full at `PIN_CAP`=6; already-pinned favicons reorder), or **right-clicked** for Pin/Unpin (`set_bookmark_pinned`, keeps the folder) + a "Move to" menu; a pinned bubble's X unpins (the bookmark stays in its folder). **Folders can be reordered** by dragging a dedicated **grip handle** on the folder header (`reorder_bookmark_folders`; drop above/below the target's midpoint). The reorder grip is a separate element rather than making the whole toggle button `draggable`, because a draggable element can swallow drops landing on it, so a favicon dropped on a collapsed target folder (whose only drop area is its header) would not move. The drop handler reads the drag **kind from the transfer payload** (`folder:<id>` vs a numeric bookmark id) rather than a mutable ref, which can go stale when a dragend doesn't fire (source element unmounted on drop). **Within a folder, favicons can be dragged onto each other to reorder** (`reorder_bookmarks` sets `position` by index; drop above/below the target's midpoint, shown by an insertion line); dropping a favicon from elsewhere onto a folder row files it there at that slot. Mutations apply **race-proof optimistic cache updates** (cancel in-flight refetches, `setQueryData`, then invalidate) so rapid successive changes (e.g. moving several bookmarks into a folder) all reflect instantly instead of a stale refetch clobbering the second. (Overlay webviews call `disable_drag_drop_handler()` so wry doesn't swallow in-page HTML5 DnD; the draggable source must be the `<button>` itself: a draggable `<div>` wrapping a button won't start a drag in WebKit.)
- **Memory / startup**: background tab webviews are discarded ("slept") after an idle threshold and recreated on focus; at launch only visible tabs spin up a webview (lazy session restore), the rest load on first show. Both are owned by `useTabWebviews.ts` (creation gated on layout visibility + a coarse idle sweep); the active tab, pinned tabs, **audibly-playing tabs** (per the `audio.rs` poll; cutting live audio mid-sound is never what the user wants, and they sleep normally once silent or muted) and the popped-out tab never sleep, and other tabs inside a **collapsed folder** are slept immediately (a collapsed folder is explicitly tucked away, so it skips the idle delay). Sleep teardown is **race-proof**: the webview map slot is held (PENDING) until the native close actually completes, so a quick wake can never spawn a second webview under the same label while the old one still tears down (the orphan would leak invisibly, still playing audio, and a later wake would double the sound); a tab that rejoined the layout mid-teardown is recreated as soon as the close lands, and close failures are logged rather than swallowed. Tunable in Settings → Performance (`tab_sleep_enabled`, `tab_sleep_minutes`); slept tabs are dimmed in the tab list via `DiscardedTabsContext`. **Wake is no longer a cold reload** (`interaction_state.rs`): just before a background webview is discarded, its WKWebView `interactionState` (back/forward list, scroll position, form data; macOS 12+) is read as base64 and cached in chrome memory (bounded, most-recent 30 sleeps); on wake `create_tab_webview` starts the webview on about:blank and applies the blob, whose restore performs its own navigation with everything intact. **Sessions also survive a full restart** (`tab_session.rs` + storage `tab_sessions` table, migration M0018): the same blob is persisted to disk **debounced**. Each finished page load marks the tab dirty and, after a ~1.2 s quiet period, `TabSessionSaver` reads its `interactionState` off the main thread and upserts it (Firefox/Safari-style periodic capture, not a per-navigation or quit-only write; a quit-time mass capture is impossible anyway, since reading from the main-thread `ExitRequested` handler would deadlock the same-thread `with_webview` hop). The chrome also persists the blob it already reads on sleep (`persist_tab_session`), so a slept-then-quit tab keeps its scrolled position. At launch, `lib.rs` purges sessions orphaned by tabs closed last run (`purge_tab_sessions_except`) and seeds the survivors into `AppState::pending_restore_states`, which `create_tab_webview` already consumes, so each tab replays its full history on its first webview creation (the active tab immediately, background tabs on first show, matching the lazy restore). A persisted blob can outlive the WebKit version that wrote it (an OS update between sessions), and `setInteractionState:` silently no-ops on an incompatible one, which would otherwise strand the tab on about:blank; the restore therefore arms a delayed guard that cold-loads the tab's URL if the webview is still on about:blank ~3 s later. Ephemeral (private) tabs never persist a session (both the capture and `persist_tab_session` skip them and drop any stale row). An evicted in-memory blob with no persisted row just cold-loads like before. **Chrome pages keep their scroll across tab switches** (`useScrollMemory.ts`): Settings/History/Downloads are React components rendered into the active pane, so switching away unmounts them (unlike a native webview tab, which is only hidden); a module-level, per-tab-id scroll store restores the container's position on remount (callback ref, so async-loaded lists restore once their rows mount). It is session-scoped (not persisted across reload), since the page's data refetches on a cold start anyway.
- **Task manager** (`memory.rs` + `TaskManagerSection`, Settings -> Performance): a live per-webview memory readout polling every 3s while the settings page is shown. Each webview's WebContent pid comes from WebKit's `_webProcessIdentifier` (guarded behind `respondsToSelector`; skipped when unavailable) and its physical footprint from `proc_pid_rusage`'s `ri_phys_footprint`, the same figure Activity Monitor's Memory column shows. Rows map labels to friendly names (tabs by title, widget panels by widget label, chrome/overlays/Peek tagged) sorted by footprint with a total, and tabs/widget panels get a one-click Close to reclaim their process. This pid+footprint plumbing is the base for memory-pressure eviction policies. **macOS only**: the command is split (`memory.rs::collect_webview_memory`) so it compiles cross-platform but degrades to an empty snapshot off macOS, because WebView2 (Windows) shares one browser process across every tab and exposes no per-webview renderer pid (the analogue of `_webProcessIdentifier`). The task manager simply shows nothing there and the widget memory-cap sweep is inert rather than wrong.
- **Resource trims**: per-workspace loopback proxies are **torn down after idling** (a 60s sweep drops a workspace's `ProxyServer` once it has had no live tab webviews for 10 minutes; `ProxyServer::drop` signals shutdown via its watch channel, and `ensure_proxy_for` lazily respawns on the next webview creation; the active workspace is exempt since Peek/widget panels always use it). `browser-state-changed` refetches are **coalesced per animation frame** (`useBrowserStateEvents` rAF guard), so a mutation burst triggers one `BrowserState` fetch, and React-Query's structural sharing returns the same reference when a refetch is a no-op, so a fired-but-empty event re-renders nothing. Components that only need a stable slice subscribe through `useBrowserStateSelector` (React-Query `select`), whose structurally-shared output skips re-rendering them when their slice is unchanged (`useSettings`, `useActivePrivacyMode`); always-mounted leaves with no or stable props (e.g. the window `Brand`) are `React.memo`'d so the per-mutation re-render of the prop-threaded chrome tree no longer cascades into them. Startup widget-favicon prefetch runs through a **concurrency cap of 4** and is **deferred a few seconds after mount**: each cold-cache prefetch takes the browser lock and the workspace proxy, and running four during launch contended with first page loads and the first widget-panel open (the dock shows letter tiles meanwhile); the launchpad quicklink prefetch is sequential by construction. `open_widget_panel`'s main-thread surface hop is awaited on the blocking pool rather than parking a tokio worker for its 500 ms cap.
- **Resilience**: WAL + `synchronous=NORMAL` (the recommended WAL pairing: integrity-safe, only the last commit is at risk on power loss, bounded by the backup) + `VACUUM INTO` backup at launch; corrupt DB is set aside and recovered from backup (or a fresh DB) so launch is never blocked and a session is never silently wiped.
- **Coalesced persistence** (`save_coalescer.rs`): every mutation snapshots the full `BrowserState`, so high-frequency bursts (drag reorders, zoom ticks, load/title sync) queue a debounced 200 ms "latest snapshot wins" write instead of one write+fsync each. Destructive transitions (close tab, delete workspace/folder, settings) still write **immediately** with rollback-on-failure. Snapshots are sequence-stamped under the state lock and the writer refuses to write older-than-committed, so a delayed debounced write can never roll the DB back behind a later immediate one; pending saves are flushed in the tauri `RunEvent::ExitRequested/Exit` hook so quitting never loses the debounce window.

## Known limitations / engine tradeoffs

Wis renders with the OS system WebView (WKWebView on macOS) via Tauri/wry, the same engine as Safari. That choice is the source of the product's wins (tiny bundle, low RAM, Safari-class speed and battery, no bundled engine to update) and dictates these limits, which are structural rather than bugs:

- **Premium DRM video (Widevine)**: WKWebView's only CDM is Apple FairPlay, not Google Widevine, and there is no API to inject a Widevine CDM (the CDM hooks the engine's media pipeline, which WKWebView does not expose). FairPlay itself is not licensed for general third-party-app playback, and services like Netflix gate on the Safari app. Result: premium DRM streaming (Netflix/Disney+/etc., especially 1080p/4K) is degraded or blocked. Mitigation is the **Open in default browser** action, not an in-app fix. Adding native Widevine would require switching to a Chromium engine (CEF) plus a Widevine license, which would forfeit the bundle/RAM/battery wins; explicitly not pursued. Note: even Firefox forks like Zen punt DRM to Firefox for the same licensing reason. **MSE + EME/FairPlay**: Wis does enable WebKit's Media Source + Encrypted Media Extensions on remote webviews (`webview_prefs::apply_media_extensions`, guarded SPI `_setMediaSourceEnabled:`/`_setEncryptedMediaAPIEnabled:`/`_setLegacyEncryptedMediaAPIEnabled:`; `UserSettings.media_extensions_enabled`, default on, toggle in Settings -> Privacy). MSE alone (off by default in embedded WKWebView) restores adaptive streaming on many non-DRM video sites; EME exposes the FairPlay key system to services that request it. This does not unlock Widevine-gated services, and Safari-app-gated FairPlay services (Netflix) still refuse, those remain the Open-in-Safari handoff.
- **Browser extensions**: an embedded WKWebView cannot load Safari Web Extensions (reserved for Safari). Wis substitutes a native blocking stack (`WKContentRuleList` + the `adblock` crate, with cosmetic filtering, scriptlets and an element picker) plus a Tampermonkey-style user-script runner, rather than a WebExtensions runtime.
- **Site isolation**: WebKit's site isolation is weaker than Chrome's (still rolling out upstream), offset by strong OS sandboxing and out-of-process rendering.
- **Other**: no cross-device sync, no mobile companion, and some newer web APIs (WebUSB/WebBluetooth/web push/PWA install) are partial or absent under WebKit. Native feature parity (cookies, biometrics, zoom, open-in-default-browser default handler) is macOS-only today.

## Build & release

- **CI** (`.github/workflows/ci.yml`): on push / PR to `main`, a matrix over macOS / Windows / Ubuntu installs deps (Linux pulls `libwebkit2gtk-4.1-dev` + packaging tools), builds the frontend, then runs `cargo fmt --check`, `clippy -D warnings`, and `cargo test`. This is the **only place the Windows (WebView2) and Linux (WebKitGTK) cfg-gated code is fully compiled**: a macOS host cannot cross-compile the `ring` C build, so platform code is otherwise isolate-verified against `webview2-com`/`windows` in throwaway crates. The first Windows/Linux run is the real validation gate for those ports (and may surface platform-specific lints to fix).
- **Release** (`.github/workflows/release.yml`): on a `v*` tag (or manual dispatch), a serialized matrix builds each OS installer via `tauri-action` and attaches them to one draft release: a universal `.dmg` (macOS), `.msi` / NSIS `.exe` (Windows), `.deb` / `.AppImage` (Linux). `bundle.targets: "all"` + `createUpdaterArtifacts` produce the signed updater artifacts, and `includeUpdaterJson` merges the per-platform entries into one `latest.json` (the matrix runs `max-parallel: 1` so that merge never races). The Linux leg additionally **strips the bundled `libwayland-*` libs from the `.AppImage` and re-signs it**: the Ubuntu 22.04 build host ships libwayland 1.20, which AppImage puts ahead of the host copy on its library path, so on newer-Mesa systems (Fedora 43 / Arch / Bazzite) EGL fails with `EGL_BAD_PARAMETER`; removing the three libs makes the AppImage fall back to the host's (every GTK system has them). A final `patch-appimage-updater` job then rewrites the now-stale Linux signature in the merged `latest.json` to match the re-signed AppImage. The Tauri updater signing key is wired; **Apple code-signing / notarization is deferred** (an unsigned `.dmg` still builds), so the updater stays effectively dormant until signing is configured.
